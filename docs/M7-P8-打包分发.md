## §2 ⚠️ 关键实测：ad-hoc 签名 + quarantine **仍然能启动**

本鱼在 Mac 上跑了多组对照实验，**结论与直觉相反**：

| 情况 | 结果 |
|---|---|
| ad-hoc 签名，**无** quarantine | ✅ 正常启动 |
| ad-hoc 签名 + quarantine，装在 `~/Applications/` | ✅ **仍然正常启动**（3 个进程） |
| ad-hoc 签名 + quarantine，放在 `/tmp/` | ❌ 不启动（**`/tmp` 的目录权限问题**，不是 Gatekeeper） |
| `open` 命令启动（带 quarantine） | ✅ 启动 |
| 直接执行 `Contents/MacOS/Tsumigeya`（带 quarantine） | ❌ 不启动（**直接执行二进制不走 LaunchServices**） |

### ⚠️ 一个关键的判据陷阱

`spctl -a -vvv -t exec Tsumigeya.app` 对 ad-hoc 签名**一律报 `rejected`**：

```
/Users/xxx/Applications/Tsumigeya.app: rejected
```

**但那只是"策略判定"，不代表真的会被拦。** 实测用 `open` 启动、装在
`~/Applications/`，**带 quarantine 也照常运行**。

→ **判据必须用「实际能不能启动」，不能用 `spctl` 的输出。**
   本鱼一开始就是拿 `spctl` 当判据，得出"ad-hoc 签名没用"的错误结论。

### ⚠️ 另一条容易误判的路

直接跑 `Contents/MacOS/Tsumigeya`（而不是 `open` app）时：
- 带 quarantine **不启动**
- 因为**直接执行二进制不走 LaunchServices**，Gatekeeper 的 quarantine
  处理路径不生效，反而被更底层的限制挡住

→ **测试必须用 `open <app>`，那才是用户的实际操作。**

## §2.1 所以「能不能双击开」到底取决于什么

实测在这个环境下：**ad-hoc 签名 + 不公证，装在 ~/Applications，`open` 能开。**

⚠️ 但这**不等于**用户下载后一定顺利：
- macOS 26 的行为本鱼只在这一台机器上验过
- 用户可能遇到"无法验证开发者"的弹窗（那取决于 quarantine 的具体标记与系统版本）

**所以 §4 的绕过指引仍然要写进 Release 说明** —— 它是保险，不是必然会发生。

---

## §3 所以 P8 能做什么 / 不能做什么

### ✅ 能做

1. **生成 .app bundle**（`Info.plist` + 图标 + 二进制）
2. **ad-hoc 签名**（`codesign -s -`）—— 这是 arm64 上**必须**的
   （完全未签名的二进制在某些情况下会被系统直接 kill）
3. **打 .dmg**（`hdiutil`）
4. **给用户明确的绕过指引**（见 §4）

### ❌ 不能做

- **公证**（需要 Developer 账号，$99/年）
- **让用户"双击即开"**（那正是公证才能给的东西）

## §4 用户拿到 dmg 后的实际操作

这是**必须写进文档/Release 说明**的内容：

```
1. 双击 .dmg，把 Tsumigeya.app 拖进「应用程序」

2. 第一次打开会被拦（"无法验证开发者"）
   两种绕过方式：

   方式 A（推荐，一次性）：
     右键点 Tsumigeya.app →「打开」→ 弹窗里再点「打开」
     之后双击就能正常开了

   方式 B（命令行）：
     xattr -dr com.apple.quarantine /Applications/Tsumigeya.app
```

⚠️ **必须告诉用户这一点**。不说明的话他会以为软件坏了 ——
而这是他第一次接触这个应用，第一印象就是「打不开」。

---

## §5 ⚠️ 为什么不能「干脆不签名」

本鱼考虑过这条路，但：

- arm64 上**未签名二进制**在某些加载路径下会被 kill（尤其有 quarantine 时）
- ad-hoc 签名**零成本**（不需要证书），且能让「无 quarantine」的情况正常工作
- 所以：**签名要做，公证做不了** —— 这两件事不是一回事
