# M5 实施方案：手柄 / 无边框全屏 / 像素缩放 / 公证分发

> **状态：已定案（2026-11-05 用户拍板三条），可以实施。**
>
> 定案记录：
> ① **无边框窗口** → **不做**（mac 真全屏本来就没边框，那是 Windows 的需求）
> ② **手柄** → **彻底删除该项**（四个引擎都原生支持，与启动器无关，见 §4）
> ③ **公证** → **不买开发者账号**，继续 ad-hoc 签名 + 把「首次打开步骤」写清楚（§5）
>
> 🔴 **本方案的结论与最初的期待有出入**：四项里有 **2 项能做**、**1 项受限**、**1 项做不了**。
> 下面每条都注明「为什么」和「实测依据」，不含乐观措辞。

---

## 0. 实测到的两个硬前提

在用户真机（macOS 26.6.2 / arm64）上查的：

```bash
security find-identity -v -p codesigning
→  0 valid identities found          ← 没有任何 Apple 代码签名证书

sqlite3 TCC.db "SELECT ... WHERE service LIKE '%Accessibility%'"
→  （空）                            ← 没有任何应用被授予辅助功能权限
```

**这两条决定了 M5 的边界**（见 §4、§5）。

## 1. 逐项可行性

| 项 | 能否做 | 难度 | 依据 |
|---|---|---|---|

## 2. 像素缩放（✅ 能做）

### 2.1 各引擎的现状（查代码 + 实测）

| 引擎 | 现有参数 | 能否加缩放 |
|---|---|---|
| **MKXP-Z** | `defScreenW` / `defScreenH` / `fullscreen` / `vsync` | ✅ 已有 `defScreenW/H`；mkxp-z 还有 `smoothScaling`（整数缩放）与 `windowScale` |
| **NW.js** | 只有 1 个参数（D61 精简过） | ⚠️ MV/MZ 靠 `ScreenScale` 与 `Graphics.resize`；**不改游戏文件就得靠 `chromium-args`**——但那正是 D53 拒绝的 |
| **EasyRPG** | 6 个参数 | 需查它的配置项（未实测，用户库里没有此引擎的游戏） |
| **Ren'Py** | 2 个参数 | Ren'Py 的缩放走 `config` 或启动参数，同样需要**改文件或设环境变量** |

### 2.2 结论与做法

**能做的是「暴露引擎自己的缩放参数」，不是「我们实现缩放」。**

```
编辑页 → 引擎参数 → 给 MKXP-Z 补 smoothScaling / windowScale 两个下拉
                   给 NW.js 若允许（见下）
```

**⚠️ NW.js 的难点**：MV/MZ 的缩放由游戏自己的 `js/rmmz.js` 决定，
外部只能通过 `--window-size` 或改 `package.json` 的 `chromium-args`。
**后者就是 D53 明确拒绝的「篡改用户游戏文件」**。

⇒ **NW.js 的像素缩放：只做 `--window-size`（不碰文件），做不出整数像素缩放就明说做不到。**

## 3. 无边框全屏（⚠️ 部分能做）

拆成两件事，**只有第一件能做**：

### 3.1 「全屏」—— ✅ 能做

| 引擎 | 手段 |
|---|---|
| MKXP-Z | `fullscreen: true` 写进 `mkxp.json`（**已实现，参数就在那儿**） |
| NW.js | `--start-fullscreen` 命令行参数（不碰文件） |
| EasyRPG / Ren'Py | 各自的启动参数（待查） |

**这部分是「把引擎已有的能力接出来」，风险低。**

### 3.2 「无边框」—— ⚠️ 受限

macOS 上让**别的进程**的窗口变成无边框，需要：

- **Accessibility 权限**（控制其他应用）+ `AXUIElement` 操作别的窗口
- 或者 **屏幕录制权限** + 自己画一层全屏覆盖窗（性能与同步都是坑）

**实测：当前 0 个应用有辅助功能权限。**

⇒ 两条路：

| 路线 | 代价 |
|---|---|
| **A（推荐）** | **不做无边框**。用引擎原生全屏（真全屏，本来就没边框） |
| B | 要求用户手动授权辅助功能 → 首次使用时弹系统提示，且在「系统设置 → 隐私与安全性 → 辅助功能」里手动勾选 |

**本鱼建议 A**：真全屏在 mac 上本来就是无边界的（macOS 原生全屏没有窗口装饰）。
「无边框窗口」是 Windows 上的需求（Windows 全屏会带标题栏时才有意义）。

## 4. 手柄 —— ✅ **不是我们的事，该项删除**

### 4.1 结论先说

**四个引擎（MV / MZ / RPG Maker 系列 / Ren'Py）全部原生支持手柄，插上即用。**
启动器**不需要也不应该**接管手柄输入（游戏是独立进程）。

### 4.2 实测证据（用户 Mac 上的真实游戏文件）

查的是**引擎核心文件**，不是某个游戏的插件：

```
Karryn's Prison/www/js/rpg_core.js   ← RPG Maker MV 引擎核心
  Input.update = function() {
      this._pollGamepads();          ← 每帧读手柄
  }
  Input.gamepadMapper = {
      0:'ok'   1:'cancel'   2:'shift'   3:'menu'
      4:'pageup'  5:'pagedown'
      12:'up'  13:'down'  14:'left'  15:'right'
  }                                  ← 标准 Xbox 布局

艾妮希雅/js/rmmz_core.js             ← MZ 引擎核心，同样有 gamepadMapper
傭兵の冒険（MKXP-Z 二进制）           ← strings 里 290 处 gamepad/joystick
```

**为什么不是「运气好」**：`rpg_core.js` / `rmmz_core.js` 是引擎自带的库文件，
游戏作者只是**没把它删掉**（删不掉，那是核心）。所以**任何** MV/MZ 游戏默认都支持。

**Ren'Py 同理**：它的 joystick 支持在引擎里（`renpy.config.joystick`），不由启动器提供。
（用户库里 5 个游戏全是 NW.js / MKXP-Z，暂无 Ren'Py 游戏，但结论不依赖这点。）

### 4.3 什么情况下游戏**会**不支持手柄

| 情况 | 说明 |
|---|---|
| 作者**覆盖**了 `Input` | 罕见，通常为了自定义按键逻辑 |
| 作者**换掉了**引擎核心 | 更罕见 |
| 用的不是这四个引擎 | 与我们无关（D60 只有 4 个引擎） |

⇒ 真遇到时，**是游戏的问题，不是启动器的**。

### 4.4 我们**不做**的事（避免将来有人"顺手"加回来）

| 不做 | 理由 |
|---|---|
| ❌ 在启动器界面里支持手柄导航 | 那是另一个需求；且 CDP/Gamepad API 只读到**我们自己窗口**的输入 |
| ❌ 手柄→键盘映射器 | 需辅助功能权限 + `CGEventPost`，会干扰前台其他应用，收益为零 |
| ❌ 显示「此游戏支持手柄」徽标 | 无法可靠判断（作者可能覆盖 Input）；猜错就是误导 |

## 5. dmg 公证（❌ 做不了）

```bash
security find-identity -v -p codesigning
→ 0 valid identities found
```

### 5.1 现在的状态

项目用 **ad-hoc 签名**（`scripts/after-pack.cjs` 跑 `codesign --sign -`）。
后果：用户首次打开会看到「无法验证开发者」，要**右键 → 打开**或去系统设置放行。

### 5.2 要公证需要什么

| 项 | 成本 |
|---|---|
| Apple Developer Program | **$99 / 年** |
| 证书申请 + 公证流程（`notarytool`） | 一次性配置，之后每次发版要跑（CI 里加 3–5 分钟） |
| 等待公证结果 | 每次几分钟 |

### 5.3 结论

**没有账号 → 无法公证。** 三条路：

| 路线 | 结果 |
|---|---|
| **A（当前）** | 继续 ad-hoc + 在 README/Release 里写清「右键打开」的步骤 |
| B | 你去买开发者账号（$99/年），本鱼把公证接进 CI |
| C | 不做 dmg，改发 zip（zip 也没签名，体验更差） |

⇒ **本方案按 A 写：把「首次打开的步骤」写清楚**，这是零成本的改善。

## 7. 三条已定案（2026-11-05 用户拍板）

| # | 问题 | 定案 | 依据 |
|---|---|---|---|
| 1 | 无边框窗口 | ✅ **不做** | mac 真全屏本无边框；「无边框窗口」是 Windows 上的需求 |
| 2 | 手柄 | ✅ **删除该项** | 四个引擎原生支持，与启动器无关（§4） |
| 3 | 开发者账号 | ✅ **不买** | 非商业项目；继续 ad-hoc + 写清首次打开步骤 |

**所以 M5 的实际范围只剩三块**：

1. **全屏与缩放参数**接进编辑页（引擎自己的能力，只是没暴露好）
2. **Release/README 写清首次打开步骤**（零成本）
3. EasyRPG / Ren'Py 的全屏参数（需实测，用户暂无这两类游戏）

## 8. 不做的事

| 不做 | 理由 |
|---|---|
| ❌ 篡改 `package.json` 的 `chromium-args` | D53 已拒：那是改用户游戏文件 |
| ❌ 合成键盘事件假装手柄（默认开启） | 需辅助功能权限，且会干扰其他应用 |
| ❌ 强制全屏（不给用户关掉的开关） | 有些游戏窗口化才好用 |
| ❌ 自签名证书伪装成可信 | 那是骗系统，也不解决问题 |
