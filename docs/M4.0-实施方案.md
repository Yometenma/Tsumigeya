# M4.0 实施方案：去掉上游 launcher（自实现启动）

> **状态：已实施完毕（S1–S7 全部完成）。** 用户 2026-11-04 决定：**「只砍 launcher，保留 module.js」**。
>
> 实施结果：508 → 634 tests（27 files），三绿。
> 端到端探针 `node scripts/probe-m40.cjs` 的结论见 AGENTS.md「M4.0 全套」。
>
> **实施中纠正/新增的结论**（与本文初稿不同的地方，都已写进 AGENTS.md）：
> 1. **§3.3 的 `dirname×3` 拼法写错了**：`mkxp.json` 实际在 `Z-Universal.app/Contents/Game/`，
>    即 `dirname×2` + `Game`（不是 `dirname×3`）
> 2. **XP 的 RTP 目录名是 `Standard`**，不是 M3 初稿推测的 `RPGXP`（实测真实 RTP.zip 的中央目录）
> 3. **§5 的迁移方案被用户推翻**：最终**不做迁移**，老用户重装引擎（D58 修订）
> 4. **`spawn` 的 ENOENT 是异步报错的**，同步 try/catch 抓不到（须手检 binary + 挂 error 监听）
>
> 前置阅读：[`docs/调研-去掉上游launcher的可行性.md`](./调研-去掉上游launcher的可行性.md)（**已实测的结论，别重复验证**）
>
> 基线：M1–M3.5 全绿，**507 tests / 20 files**，v0.3.2 已发布。

## 1. 为什么做

### 1.1 三个动机

| # | 动机 | 严重度 |
|---|---|---|
| **A** | **不再修改用户的游戏文件**（上游 nwjs 会改写 `js/main.js`、塞 `js/plugins/Cheat_Menu.js`、改 `package.json`） | ⭐⭐⭐⭐ |
| **B** | **摆脱「必须共享 `xenolauncher` 数据目录」**（D3 的由来） | ⭐⭐⭐ |
| **C** | **清掉一批补丁式代码**（`reconcileVersionArgs`、nwjs 二进制预检查） | ⭐⭐⭐ |

### 1.2 顺带的额外收益

- 进程追踪变**简单**（自己 `spawn` 直接有 PID，不用劫持 `exec`）
- 启动失败**有真实错误**（`spawn` 的 ENOENT 会抛，上游 `exec` 只 `console.error`）

### 2.2 各引擎的可执行文件路径（**照抄，否则装好的引擎找不到**）

## 3. 架构：新增 `src/main/launchers/`

### 3.1 结构

```
src/main/launchers/
├── index.ts        ← 入口：buildLaunchCommand(engine, ctx) → { binary, args, cwd, prelude }
├── binary-paths.ts ← ★ 所有引擎的可执行文件路径（**唯一来源**，R4）
├── nwjs.ts
├── mkxpz.ts
├── easyrpg.ts
└── renpy.ts
```

### 3.2 统一接口

```ts
export interface LaunchContext {
  /** 游戏根目录（已解析成绝对路径）。 */
  folder: string
  /** 用户的原始 gamePath（可能是文件夹里的某个 exe）。 */
  gamePath: string
  /** 引擎参数（已经过 reconcileVersionArgs）。 */
  gameArgs: Record<string, unknown>
  /** 游戏标题（renpy 拿它当存档目录名）。 */
  gameTitle: string
  /** 数据目录（引擎模块所在处）。 */
  dataDir: string
  platform: NodeJS.Platform
  arch: string
}

export interface LaunchPlan {
  /** 要执行的二进制绝对路径。 */
  binary: string
  /** 参数数组（**不要拼成字符串**——自己 spawn 要 argv 形式，天然免转义问题）。 */
  args: string[]
  /** 工作目录。 */
  cwd?: string
  /**
   * 启动**前**要做的事（写配置文件等）。
   * 返回 void；抛错 = 启动前置失败，**游戏不会被拉起**。
   */
  prepare?: () => void | Promise<void>
}

/** 不认识的引擎返回 null（调用方决定怎么处理）。 */
export function buildLaunchPlan(engine: string, ctx: LaunchContext): LaunchPlan | null
```

**为什么用 `args: string[]` 而不是拼命令行字符串**：
- `spawn(binary, args)` 天然处理空格/中文/引号，不用自己写 `quote()`
- 上游那些 `quote()` 函数就是在补这个坑

### 3.3 各引擎实现要点

#### nwjs（最复杂，但必需逻辑仍很少）

```ts
export function nwjsPlan(ctx: LaunchContext): LaunchPlan {
  const version = String(ctx.gameArgs.version ?? '')
  const binary = nwjsBinaryPath(ctx.dataDir, version, ctx.arch)
  // ⚠️ 不做：copyCheatFiles / modifyMainJs / applyProtection / chromium-args 篡改
  return { binary, args: [ctx.folder], prepare: checkBinaryExists(binary) }
}
```

**注意**：上游改了 `package.json` 的 `chromium-args`。我们**不改**——
待实测确认：不改会不会影响游戏运行（见 §8 R2）。

#### mkxpz

```ts
export function mkxpzPlan(ctx: LaunchContext): LaunchPlan {
  const binary = mkxpzBinaryPath(ctx.dataDir)
  const gameDir = path.join(path.dirname(path.dirname(path.dirname(binary))), 'Game')
  return {
    binary,
    args: [],
    prepare() {
      // 复用 diagnose.ts 的推断 + 上游的 passthrough 语义
      const { rtp, rgssVersion } = resolveRtpFor(ctx.folder, ctx.gameArgs)
      const config = { gameFolder: ctx.folder, RTP: rtpArray, rgssVersion, ...passthrough }
      fs.mkdirSync(gameDir, { recursive: true })
      fs.writeFileSync(path.join(gameDir, 'mkxp.json'), JSON.stringify(config, null, 4))
    }
  }
}
```

#### easyrpg / renpy

直接照上游拼（参数简单），见 §2.3。

### 4.1 `launch()` 重写后的形状

```ts
const plan = buildLaunchPlan(game.gameEngine, { folder, gamePath, gameArgs, gameTitle, dataDir, platform, arch })
if (!plan) throw failure('error.launchUnsupported', `引擎 ${engine} 暂不支持自实现启动`)

// 前置（写配置文件等）失败 = 不启动
await plan.prepare?.()

// macOS quarantine（保留）
if (platform === 'darwin') void runFile('/usr/bin/xattr', ['-dr', 'com.apple.quarantine', folder])

const child = spawn(plan.binary, plan.args, { cwd: plan.cwd ?? folder, detached: true, stdio: 'ignore' })
// ↑ detached + stdio:'ignore' = 游戏独立活下去，Tsumigeya 退出也不带走它
child.unref()

registry.addFromChild(id, child, engine, plan.binary)   // 直接有 pid
```

**`detached: true` 很重要**：否则关掉 Tsumigeya 会把游戏一起杀掉。

## 5. 数据目录：切到 `Tsumigeya`，**不做迁移**（用户 2026-11-04 定，取代本节初稿）

初稿给了两个选项让用户定（保持现状 / 切换+迁移），**用户先选「切+迁移」，随后改口**：

> 「哦算了，你推荐得不行，我还是尽量不想要和上游还有关系」→「重新装引擎吧」

最终决定（D58 修订）：

- ✅ **数据目录切到 `~/Library/Application Support/Tsumigeya`**
- ✅ **不实现迁移逻辑**：不认旧目录、不读旧目录、不 rename、不复制
- ✅ 老用户重装引擎（nwjs ~200MB + mkxpz ~100MB + RTP 244MB），**游戏库也要重新添加**

**为什么「不迁移」反而是对的**：

| 角度 | 说明 |
|---|---|
| 代码彻底干净 | 迁移代码必然要写一份旧目录字符串做判断 → 代码里永远留着 `xenolauncher`，与「不想和上游有关系」直接冲突 |
| 迁移是半吊子的 | 只搬 `modules` + 索引文件，搬不动存档本体（各引擎在自己的目录里），用户会得到「引擎在、存档没了」的更糟状态 |
| 两边会打架 | 搬走之后用户若还想用原版 Xenolauncher，两个程序共享同一批文件的副本，互相覆盖 |
| 用户明确表态 | 用户在本会话亲口说「重新装引擎吧」，不需要为省一次下载写一套长期负债 |

**连带影响（必须在 S7 的 UI 里交代）**：

- 首次打开新目录是空的 → 引擎管理页显示「未安装」；游戏库为空
- 需要**中文提示**告诉用户发生了什么（`error.dataDirSwitched` 之类的 info 级说明），
  绝不能静默地让用户以为「我的游戏全丢了」（v0.3.2 及更早的用户会踩到）

### 5.1 代码上的落点

`core-host.ts` 的 `resolveDataDir()`（mac 分支）改一个字符串：

```ts
if (platform === 'darwin') {
  return path.join(home, 'Library', 'Application Support', 'Tsumigeya')  // ← 唯一一处改动
}
```

**没有** `migrateLegacyDataDir()`，**没有** 迁移测试。S6.5 因此从「迁移逻辑 + 迁移测试」
缩减为「改一个字符串 + 一条防回归测试（断言 mac 分支不含旧目录名）+ 首启提示文案」。

## 7. 风险

| # | 风险 | 处置 |
|---|---|---|
| **R1** | 自己拼的路径与上游不一致（装好的引擎找不到） | **照抄 §2.2 的拼法**；单测钉死；生产失配时报可读错误（含期望路径） |
| **R2** | 不篡改 `package.json` 的 `chromium-args` 是否影响游戏运行 | **必须真机对比**：同一游戏用上游启动 vs 自实现启动，看行为差异。若无差异就不改；若有差异，评估是否加那一个参数 |
| **R3** | NW.js 可能有子进程树，一个 PID 杀不干净 | M3.5 §9 R4 已记；自实现后可考虑 `detached` 起新进程组，用 `process.kill(-pid)` 整组杀 |
| **R4** | 上游未来改了 binary 路径 | 路径拼法**集中在一个文件**（`binary-paths.ts`），只改一处 |
| **R5** | 数据目录切换导致老用户引擎/游戏库「消失」（新目录是空的） | 用户已决定**不迁移、重装引擎**（见 §5 / §10-②）。必须给一次性中文说明（info 级，别每次启动都弹），绝不能静默 |
| **R6** | `spawn` 失败（ENOENT / EACCES） | 直接抛 `error.launchFailed` + 带上 binary 路径；**比上游的静默 console.error 好** |

## 8. 新增决策

| # | 决策 | 理由 |
|---|---|---|
| **D53** | **自实现启动，不用上游 `launcher.js`**；`module.js` 保留 | 上游 99% 是附加功能（含**改写用户游戏文件**）；自实现后默认不碰游戏目录 |
| **D54** | 用 **`spawn(binary, args[])`** 而不是拼命令行字符串 + `exec` | `args` 数组天然处理空格/中文/引号，不用自己写 `quote()`（那正是上游在补的坑）；且 `spawn` 直接给 `ChildProcess`（M3.5 的注入方案随之作废） |
| **D55** | 用 `detached: true` + `stdio: 'ignore'` + `child.unref()` | 否则**关掉 Tsumigeya 会把游戏一起杀掉**；游戏应该独立存活 |
| **D56** | 所有引擎可执行文件路径**集中在 `launchers/binary-paths.ts`** | 上游改了路径时只改一处；也便于单测覆盖 4 个引擎 × 2 个架构 |
| **D57** | **未知引擎不回退上游 launcher**，明确报 `error.engineNotLaunchable` + 引擎页标灰 | 上游 6 个模块里不做的是 ruffle（Flash，用户已不用）/ wine（Windows，用户有 CrossOver）/ macos（本项目就是给 macOS 用的，再装一个 macOS 原生引擎没意义）。回退机制等于为不会发生的场景维护代码，且**回退那条路径会改游戏文件** |
| **D58** | 数据目录从 `Xenolauncher` 切到 **`Tsumigeya`**，**不迁移、不探测旧目录**；老用户重装引擎、重新添加游戏；首次运行给一次性中文说明 | 与上游共享目录的初衷是「上游 launcher 硬编码那个路径」，M4.0 后不再用 launcher → 约束消失。**不做迁移**是用户 2026-11-04 改口后的最终决定：迁移会在代码里永久留下旧目录字符串，且只能搬索引搬不动存档，与「尽量不和上游有关系」的目标冲突（详见 §5） |

## 10. 用户已拍板（2026-11-04）

| # | 问题 | **决定** |
|---|---|---|
| 1 | 未知引擎是否回退上游 launcher | ❌ **不回退** |
| 2 | 数据目录是否切到 `Tsumigeya` | ✅ **切**（**不含迁移**，用户改口：重装引擎） |
| 3 | 是否保留作弊注入 / DOM 保护 | ❌ 不做 |
| 4 | 是否顺便统一存档目录约定 | 留到 M4 存档管理 |

### 10-① 为什么「不回退」成立

上游仓库实际有 **6 个**模块，我们只实现 4 个：

```
easyrpg / mkxpz / nwjs / renpy   ← 我们实现
ruffle（Flash）/ wine（Windows BETA）/ macos（macOS 原生）  ← 不做
```

**用户 2026-11-04 给出的三条理由（全部成立）**：

1. **Flash 现在很少有人用**（ruffle）
2. **本项目就是「在 macOS 上玩 DLsite 同人游戏」**，专门再装一个「macOS 原生游戏」引擎没意义
3. **Windows 游戏用户已有 CrossOver**（wine 那个模块自己标着 "IN BETA"）

**结论**：不实现的那 3 个引擎，用户本来就不会用。回退机制等于为「不会发生的场景」维护一套代码。

**收益**：
- ✅ `exec-inject.ts` **可以彻底删除**
- ✅ 代码里没有「一条走新路径、一条走老路径」的分叉
- ✅ **绝不修改任何游戏文件**（老路径那条会改）

### 10-①-a 但「不回退」必须定义清楚失败行为

**边界场景**：用户已装了 ruffle / wine / macos 模块，点启动会怎样？

**不能静默失败**（用户会以为「点了没反应」）。方案：

```ts
const plan = buildLaunchPlan(engine, ctx)
if (!plan) {
  // 明确告诉用户：这个引擎类型暂不支持启动
  throw failure('error.engineNotLaunchable', ...
    '引擎 "{engine}" 暂不支持启动。
' +
    '本版本支持：NW.js（MV/MZ）、mkxp-z（XP/VX/VX Ace）、EasyRPG（2000/2003）、Ren'Py。')
}
```

**并且**：在「引擎管理」页把不支持启动的引擎**标灰或加说明**，
而不是让用户装完才发现不能用。

> 这是「不回退」的必要配套——**决定不回退 ≠ 可以静默失败**。

### 10-② 数据目录切到 `Tsumigeya`，**不迁移**（D58 修订）

**现状**（D3）：`~/Library/Application Support/Xenolauncher`（与上游共享）
**改成**：`~/Library/Application Support/Tsumigeya`

**涉及代码**：`core-host.ts` 的 `resolveDataDir()`（**唯一一处**）

```ts
if (platform === 'darwin') {
  return path.join(home, 'Library', 'Application Support', 'Tsumigeya')  // ← 改这里
}
```

#### 初稿曾要求「必须迁移」，**用户随后推翻**

初稿的理由是「老用户引擎（nwjs 200MB + mkxpz 100MB + RTP 244MB）在旧目录，
切路径后要重下几百 MB，体验差」。曾设计过三套迁移方案（rename / 复制 / 软链）。

**用户 2026-11-04 的原话**（两次表态，第二次是改口）：

> 「哦算了，你推荐得不行，我还是尽量不想要和上游还有关系」→「重新装引擎吧」

**最终不迁移，四条理由**：

| # | 理由 |
|---|---|
| 1 | 迁移代码必然要写一份旧目录字符串做判断 → 代码里**永远留着** `xenolauncher`，与「不想和上游有关系」直接冲突 |
| 2 | 迁移是**半吊子**：只搬 `modules` + 索引，搬不动存档本体（各引擎在自己目录里）→ 用户得到「引擎在、存档没了」的更糟状态 |
| 3 | 搬走之后用户若还想用原版 Xenolauncher，两个程序共享同一批文件的副本 → 互相覆盖 |
| 4 | 用户已明确表态要重装，不需要为省一次下载背上长期负债 |

#### 但要交代清楚（否则就是静默失败）

新目录首次运行为空：引擎管理页全部「未安装」、游戏库空白。
**v0.3.2 及更早的用户会直接踩到**（他们机器上已装着引擎与游戏库）。

所以在 S7 必须给一条 **info 级中文说明**（不是 error，不是静默）：

```
数据目录已切换到 Tsumigeya。
引擎与游戏库需要重新添加（旧目录里的数据不会被读取，也不会被删除）。
```

判据：**只在「新目录里没有 modules 且没有 games.json」时提示一次**
（用一个 `firstRunNoticeShown` 标记落进 global-settings，别每次启动都弹）。

#### 不要做的事

- ❌ 不要 `fs.renameSync` / `fs.cpSync` 旧目录（用户已否决迁移）
- ❌ 不要 `fs.existsSync` 去探测旧目录（探测就会有人接着写「顺手搬一下」）
- ❌ 不要删旧目录（那是用户自己装的另一套东西，不归我们处置）
