# 技术选型：三条路线的真实代价

> 结论先行：**推荐「宿主可替换」的 Electron + Web 前端路线**，但不推翻现有 nw.js 出包流程。
> 核心引擎管理逻辑（module.js）三个方案都能原样复用，真正要重写的只有 UI。

---

## 一、现状盘点（基于实际代码，不是猜的）

| 部件 | 位置 | 规模 | 说明 |
|---|---|---|---|
| 核心管理逻辑 | `app/module.js` | 1870 行 | **UMD 双宿主设计**，文件头原注释写着 "The same core is used by NW.js and the native launcher's Node helper" |
| HTML 前端 | `app/*.html` + `*.js` | 约 5000 行 | 全英文，7 个页面（主界面 / 游戏设置 / 全局设置 / 模块管理 / 状态 / 版本管理 / 游戏编辑） |
| SwiftUI 前端 | `native/Sources/*.swift` | 1643 行 | 13 个文件，已有游戏列表、动态参数表单、引擎管理、设置、更新检查、中英双语 |
| Swift 的 Node 后端 | `native/Backend/worker.cjs` | 410 行 | JSON-lines over stdio，18 个命令（detect / install / launch / snapshot / update…） |
| 引擎模块 | 外部仓库 `Xenolauncher-Modules` | 7 个模块 | mkxpz / easyrpg / nwjs / renpy / ruffle / wine / macos，每个含 `manifest.json` + `launcher.js`（CommonJS） |
| 构建 | `.github/workflows/` | 2 个 workflow | 在 `macos-latest` / `macos-15-intel` 上打 nw.js 的 .app |

**关键事实**：这个项目不是「一个前端」，而是「一个引擎模块系统 + 两套前端」。模块系统的抽象（manifest 声明依赖、gameArgs 声明设置项、autodetect 声明识别规则）是干净的，这部分**任何方案都不用重写**。

**关键风险**：`module.js` 里硬编码了 macOS 路径（`~/Library/Application Support/Xenolauncher`）和 `os.arch()` 到 `universal/arm64/x86_64` 的映射。想在 Windows 上开发调试，这层路径必须抽象出来。

**许可证**：原项目 GPL-3.0。基于它的代码做衍生分发，**必须开源并保留 GPL**。如果要闭源，只能「参考架构、代码重写」。

---

## 二、三个方案

### 方案 A：留在 nw.js，只重做 UI

**做法**：保留 `app/` 的壳和 `module.js`，把 7 个 HTML 页面用新的中文界面重写，样式现代化。

**要写的东西**：CSS/HTML/JS 重写约 2400 行 + 中文文案 + 封面网格布局。
**不用写的东西**：模块系统、安装、检测、启动、CI 打包——全都能用。

| 项 | 评价 |
|---|---|
| 核心逻辑复用 | 100%，一行不用改 |
| UI 开发速度 | 中。HTML/CSS 迭代不难，但 nw.js 的工具链是石器时代（没有 Vite、没有热更新、改完刷新） |
| **能否在 Windows 上开发** | ✅ 能。nw.js 有 win-x64 版（203 MB），UI 可以在本机直接看效果 |
| 体积 | 差。arm64 SDK 版 165 MB / 正式版 147 MB（解压后更大），因为要带着整个 Chromium |
| macOS 原生感 | 差。窗口、菜单、Dock、托盘都得手写 nw API，且 nw.js 社区已很小 |
| 签名分发 | 麻烦。deep sign 一堆 framework，CI 里已经用 `codesign --force --deep -s -` 凑合 |
| 长期维护 | 风险最高。nw.js 版本落后，未来 Chromium 安全更新靠社区 |

**工时估算**：2～3 周（业余时间按 4～6 周）。

---

### 方案 B：Electron + 现代前端（Vue 3 或 React + Vite），保留模块系统

**做法**：Electron 主进程 `require('./module.js')` 直接当库用（它就是为多宿主设计的 UMD），渲染进程用 Vite 起一个现代前端，通过 IPC 桥调用。

**要写的东西**：IPC 桥（约 300～500 行）+ preload 白名单 + 全新中文 UI。
**不用写的东西**：模块系统的任何业务逻辑。

| 项 | 评价 |
|---|---|
| 核心逻辑复用 | 95%+。`module.js` 挂到主进程即可，只需把 `getAppSupportDir()` 注入进去（它本来就接受 services 注入） |
| UI 开发速度 | **最快**。Vue/React + Tailwind + 组件库，封面卡片、标签筛选、动态表单都是现成套路，改一行热更新 |
| **能否在 Windows 上开发** | ✅ 完全能。Electron 在 Windows 上跑 UI、跑模块逻辑、跑大部分单测 |
| 体积 | 中。arm64 打包约 100～150 MB（比 nw.js 略小，但仍带 Chromium） |
| macOS 原生感 | 中。需要自己写菜单栏、Dock 菜单、`open-file` 事件；配合 electron-builder 也能做得不错 |
| 签名分发 | 成熟。electron-builder 一条命令出 dmg + 公证（`notarytool`），生态文档齐全 |
| 长期维护 | 最好。Electron 有微软/社区长期维护，Node 版本随时升级 |

**工时估算**：3～4 周（桥 3～5 天 + UI 2～3 周）。

---

### 方案 C：SwiftUI 原生（项目已经有一半骨架）

**做法**：继续 `native/` 目录，把 1643 行扩成完整 App，Node 逻辑继续走 `worker.cjs` 子进程。

**要写的东西**：所有 UI（网格、封面缓存、Markdown 说明、动态参数表单、文件选择器）+ 打包 node 运行时（`build.sh` 已经在 `cp` 一份 node 二进制进 bundle）。
**不用写的东西**：`worker.cjs` 已有 18 个命令，覆盖了主要功能。

| 项 | 评价 |
|---|---|
| 核心逻辑复用 | 80%。worker.cjs 是重写的中间层，不是 module.js 原样，长期会和上游分叉 |
| UI 开发速度 | **最慢**。SwiftUI 写封面网格/图片缓存/富文本说明都要自己搭；改一次要等编译 |
| **能否在 Windows 上开发** | ❌ **完全不能**。Swift 只能 Mac 上编，你人在 Windows，等于闭眼写 |
| 体积 | 最好。App 本体约 10 MB + node 二进制约 50 MB，总体比 Chromium 方案小 |
| macOS 原生感 | 最好。菜单栏、Spotlight、Quick Look、系统分享、拖拽、无障碍全是白送的 |
| 签名分发 | 最规范。Xcode 直接 archive/notarize，还能上 Mac App Store（虽然 GPL 有冲突风险） |
| 长期维护 | 中。跟着 Apple 走，但你要一直懂 Swift；`worker.cjs` 与上游 `module.js` 双份维护是隐患 |

**工时估算**：4～8 周，且**只能在你 Mac 上做**，本鱼在 Windows 这边帮不上验证的忙。

---

### （附）Tauri 为什么不在推荐里

体积确实小（约 15 MB），但要 Rust 写主进程，模块脚本得打成 sidecar 子进程，等于把方案 C 的「跨进程调试」痛苦搬过来还多学一门语言。**「省 100 MB 换两周工期 + 一门新语言」不划算**，除非你特别在意安装包大小。

## 四、推荐：方案 B，但加一个「宿主抽象」的设计

### 为什么是 B

1. **你人在 Windows，但目标平台是 macOS** —— 这是最硬的约束。SwiftUI 你只能在自己 Mac 上盲写盲改，反馈周期从「秒」变成「分钟到小时」。Electron 让你在本机就能跑起整个 UI 和引擎逻辑，只有最后的打包才需要 Mac / GitHub Actions。
2. **`module.js` 是 UMD，天生为多宿主写的** —— Electron 主进程直接 `require()` 就能接管 7 个引擎模块的安装与启动，这是这个项目最值钱的资产，别扔。
3. **你要的 7 项功能，6 项是 UI 和数据处理，1 项是外壳能力** —— 中文界面、自动扫描、DLsite 元数据、存档管理、增强菜单，全是 Web 前端的舒适区。手柄走 Gamepad API（Electron 支持良好）。
4. **分发** —— `electron-builder` + `notarytool` 是成熟流水线，GitHub Actions 上出 dmg 比现在 deep-sign nw.js 干净得多。

### 架构建议：把「宿主」抽成一层

```
Tsumigeya/
├── core/                    # 引擎模块管理（fork 自 module.js，GPL-3.0）
│   ├── module.js            #   原样搬过来，路径/平台差异从外部注入
│   ├── paths.js             #   PlatformPaths：macOS 用 ~/Library/Application Support，Windows 用 %APPDATA%
│   └── detect.js            #   自动扫描 + 引擎识别（新增）
├── app/                     # Electron 主进程
│   ├── main.ts              #   require('../core/module.js')，注册 IPC
│   ├── preload.ts           #   白名单桥，不暴露 node
│   └── services/            #   dlsite.ts（RJ 号抓元数据）、saves.ts（存档扫描/备份）、inject.ts
├── renderer/                # 前端（Vue3 + Vite + Tailwind）
│   ├── pages/               #   游戏库 / 引擎 / 设置 / 存档
│   └── i18n/zh-CN.json      #   中文文案集中管理（以后加英文只需加一份 json）
└── modules/                 # 引擎模块源（可在设置里切换上游仓库或自己的镜像）
```

**关键设计点**：`core/` 不 import 任何 Electron API，只接受注入的 `{ paths, ui }`。这样：
- 现在就能用 `nw.js` 出个能跑的包（CI 现成的），
- 以后换 Electron、甚至做 CLI 工具，`core/` 一行不用改。

## 五、建议的分阶段路线

| 阶段 | 目标 | 交付物 | 预估 |
|---|---|---|---|
| **P0** | 跑通现状 | 在你 Mac 上把 nw.js 版打出来，确认至少一个 DLsite 游戏能启动 | 半天 |
| **P1** | 中文骨架 | Electron 壳 + IPC 桥 + 中文游戏列表/设置页，能添加、启动游戏 | 1 周 |
| **P2** | 自动入库 | 拖入文件夹 → 自动识别引擎（XP/VX/VA→mkxp-z，MV/MZ→nw.js，2000/2003→EasyRPG，Ren'Py）、自动装对应引擎 | 1 周 |
| **P3** | DLsite 元数据 | 输入 RJ 号 / 自动从文件夹名识别，抓标题、社团、封面、标签、发售日 | 3～5 天 |
| **P4** | 故障自愈 | RTP 缺失检测、字体缺失（中文乱码/方块）、黑屏、编码修复；一键「修复启动」 | 1 周 |
| **P5** | 存档与增强 | 每游戏存档集中查看/备份/导出；注入 Cheat Menu、变速 | 1 周 |
| **P6** | 打磨与分发 | 手柄、无边框全屏、像素缩放；electron-builder 出 dmg + 公证 | 1 周 |

**先做 P1 + P2 就有 80% 的爽感**，P3 是「哇」的瞬间。

## 六、需要你拍板的三件事

1. **选 A / B / C？**（本鱼推荐 B）
2. **这个项目要开源吗？** 基于现项目就是 GPL-3.0 衍生，必须开源（可以晚点发布）。如果你不想开源，那只能「看架构、自己重写」，工作量翻倍但自由度更高。
3. **P1 先做哪一块？** 我建议先做「游戏库 + 自动识别 + 中文界面」，因为这是每天都要看的东西。
