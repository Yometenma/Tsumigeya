# M7 — SwiftUI 原生重写方案

> **状态**：方案待用户拍板。尚未写任何实现代码。
> **触发**：用户 2026-11-06 明确要「用 Swift/SwiftUI 重写，真正的 native」。
> **前置事实**：当前 Electron 版**已经是正经 macOS app**（.app/.dmg、真 Mach-O、ad-hoc 签名、
> 已在 Mac 真机验收过）。重写**不是修 bug，是换实现栈**——收益是「原生感」，
> 代价见 §6。这个判断不因方案写得漂亮而改变。

---

## §1 为什么值得做（收益是真的）

| 收益 | 具体是什么 |
|---|---|
| **原生控件与系统集成** | SwiftUI 的 List / Table / Form / 侧边栏是 AppKit 原生控件。滚动惯性、右键菜单、拖拽、全屏、VoiceOver、主题色跟随、`⌘,` 偏好设置窗口——都是系统白送的，不用自己仿 |
| **启动与内存** | Electron 冷启 ~1.2s、常驻 ~180MB（空窗）；SwiftUI 预期 ~0.4s / ~60MB。对「一个启动器」来说，这个差距在体感上确实明显 |
| **菜单栏正确性** | Electron 的 mac 菜单栏要手工搭，且默认带几个英文项；SwiftUI 的 `MenuBarExtra` / 标准菜单是自动且中文的 |
| **应用体积** | 现在 dmg ~130MB（打包了 Electron）。原生预期 ~15–25MB。**这一条最直观** |
| **不再有 Chromium 层** | 少一层可更新面、少一处安全面、少一类「GPU process crashed」日志 |

⚠️ 但**收益里没有「能跑更多游戏」**——识别/启动逻辑与 UI 框架无关，
重写不会让任何现在跑不起来的引擎跑起来。这一点必须先说清。

## §2 硬骨头（四条，全是踩过的坑，重写必须重踩一遍）

本鱼已经在 Mac 真机上把四条**逐一实测**过（`ssh yometenma@192.168.1.86`，Xcode 27.2 / Swift 6.4.2）：

### R1 — mkxp-z 的非 ASCII 陷阱（D71/D72）

- **实测**：Swift 建 symlink 到 `~/games/苍蓝星` → ✅ 成功，解析回正确路径
- **实测**：GBK 解码（`CFStringEncodings.GB_18030_2000`）→ ✅ 可用
- **但**：D72 的核心不是「能不能建 symlink」，而是**mkxp-z 自己见到非 ASCII 字节就判失败**
  （它的 JSON 读取器先做编码嗅探）。这条约束原样存在，与实现语言无关。
- **结论**：Swift 版**必须**保留「ASCII 符号链接 + 配置写 app 包内 + 不传 cwd」这套处置。
  这部分是**照抄**，不是重写。

### R2 — 进程分离（D55）

- **实测（强证据）**：Swift 里 `Process` + `FileHandle.nullDevice` × 3 spawn 一个 `sleep 30`，
  然后**让 Swift 进程 `exit(0)` 立刻退出** → `sleep` 的 PID 44965 **仍然存活**，
  且 `ps` 的 TTY 列显示 `??`（已脱离终端，由 launchd 收养）。**D55 在 Swift 下成立**。
- **注意**：Swift 的 `Process` **没有** Node 的 `detached: true` / `child.unref()`，
  但上面实测表明它**天然不随父进程死**——所以不需要额外做什么，**但要留住这条验证**。
- **仍待验的一点**：SwiftUI app（有窗口、有 `NSApplication` 生命周期）退出时行为是否一致。
  上面验的是命令行 `exit(0)`，不是 `NSApplication.terminate`。P2 阶段要在真 app 里再验一次。

### R3 — 解压（M1 §4）

- **实测**：`FileManager` **没有** unzip（`responds(to: unzipItem)` = false）
- **现状**：Electron 版走系统 bsdtar（`/usr/bin/tar`），并踩过
  「mac 的 bsdtar 在 `LANG` 为空时把非 ASCII 文件名输出成八进制转义」的真 bug。
- **Swift 版三条路**：
  - (a) 继续调 `/usr/bin/tar`（**推荐**）：与现在完全一致，那个 LANG 坑的处置直接复用
  - (b) `Process` + `/usr/bin/ditto -x -k`（Apple 自家，处理 zip 更稳）
  - (c) 引第三方 SwiftPM 包（如 ZIPFoundation）→ 新增依赖与维护面
- **结论**：走 (a)/(b)，**不引入新依赖**。

### R4 — ZIP 打包/导入（存档导出，D81/D82）

- Electron 版用 `fflate`（纯 JS）。Swift 有 `NSFileCoordinator` + `FileManager`，
  也可以继续用 `ditto`。**这一条比 R3 轻**，但 sha256 校验、原子写、
  备份幂等的**顺序**（校验→备份→才写）必须原样保留——那是防丢档的判据。

| **shared 纯判据** | 3613 | **照搬**。这些是纯函数（筛选、时长分级、存档三态、批量选择…），逐条翻译，**78 个测试文件就是验收清单** |
| **UI** | 7785 | **真重写**。但这里恰恰是 SwiftUI 最省力的部分——List/Form/Sidebar 是系统控件 |
| **preload** | 140 | **整个消失** |

**净估算**：

- **可以照搬/翻译**：约 **13000 行**（但翻译不是复制，是重按判据实现一遍）
- **净删除**：约 **2000 行**（IPC + preload）
- **真重写**：约 **7800 行 UI**
- **总量**：Swift 版预期 **12000–15000 行**（比现在少，因为扔掉了整层 IPC 与 Chromium 适配）

## §4 分阶段（每阶段都必须能独立验收）

> 原则：**不推倒重来**。每一步都留下一个能跑的东西，随时可以停。
> 判据来源：现有 **78 个测试文件 / 1592 条测试** 是现成的验收清单，
> 逐条移植成 Swift Testing / XCTest。

| 阶段 | 内容 | 验收判据 | 预估 |
|---|---|---|---|
| **P0 骨架** | SwiftPM/Cocoa app 骨架 + 数据目录 + JSON 读写 | 能读现有 `games.json`（5 个真游戏）并列出 | 小 |
| **P1 引擎层** | registry（照搬数据）+ 识别 + manifest + 版本比较 | 移植 `engines-*` 测试（~120 条）；对 5 个真实游戏**识别结果与 Electron 版逐个一致** | 中 |
| **P2 启动层** | binary-paths + spawn + 9 个引擎参数 | **真机启动 4 个 nwjs + 1 个 mkxpz**，关掉启动器后游戏存活（R2） | 中 |
| **P3 装/更新** | 下载 + 解压（R3）+ 安装/更新/卸载 | 重装 nwjs 成功；`updateEngine` 多版本保留不变量 | 中 |
| **P4 库 UI** | SwiftUI 库页 + 详情页 + 编辑页 | 5 个真游戏能显示海报墙、进入详情、启动 | **大** |
| **P5 引擎页 + 设置页 + 向导** | | 各页功能对齐 | 大 |
| **P6 存档** | 探测 + 列表 + 导出/导入 | 对真实存档目录**导出→比对 sha256→破坏→导入→精确还原** | 中 |
| **P7 DLsite** | 抓取 + 缓存 + 编辑字段 | 对一个真 RJ 号抓取成功 | 中 |
| **P8 收尾** | 图标（已有）、公证、CI | 出 dmg 并真机装 | 小 |

**关键**：P0–P3 是**纯逻辑层**，可以在 Mac 上无 UI 验证，风险低。
P4–P5 才是真正的大头（UI），但那时逻辑层已经稳了。

## §5 能与现有 Electron 版共存吗

**可以，而且应该**：

- 数据目录**同址**（`~/Library/Application Support/Tsumigeya`）——两边都能读写
- 引擎模块目录**同址**（`modules/<引擎>/`）——已装的 1.1GB 不用重下
- **风险**：两边同时写 `games.json` 会冲突。P 阶段期间建议**不要并行使用**，
  或用不同的 `TSUMIGEYA_DATA_DIR` 隔离
- App 名/图标复用（`build/icon.icns` 已就绪，本鱼刚做的）

## §6 代价（必须先看这一段）

| 代价 | 说明 |
|---|---|
| **开发机不在手边** | 开发机是 Windows。Swift 只能通过 `ssh` 在 Mac 上编译——**能验，但每一轮都要往返**。本鱼能连（已实测），但这不是本机开发 |
| **78 个测试要移植** | 这是**最被低估的成本**。1592 条测试是这套代码真正的资产，移植不是复制粘贴 |
| **一次性丢失的战斗经验** | D50/D52/D55/D69/D71/D72/D81/D82/D85/D86 这一整桌坑，重写时**都会重踩一遍**。文档在，但「为什么这么写」的直觉会丢 |
| **双栈维护期** | P0–P8 期间两套并存，改一个 bug 可能要改两处（或明确放弃旧栈） |
| **公证仍未解决** | SwiftUI 不改变「没证书 → 首次右键打开」这件事。公证要 Apple Developer Program（¥688/年），与实现栈无关 |
| **进度不可压缩** | 7800 行 UI 就是 7800 行。快不了 |

## §7 本鱼的建议

**做，但按 P0→P3 先跑一遍，不要一次梭哈。**

理由：

1. P0–P3 是**纯逻辑层**，有 13000 行可参照 + 120 条引擎测试可移植，
   **在 Mac 上无 UI 就能验证**。跑通这三步，你就知道「Swift 版能不能真的跑起游戏」——
   这是整个重写成立与否的**唯一硬判据**
2. 如果 P0–P3 卡住（比如 R2 进程分离验不过、或 mkxp-z 的 ASCII 处置在 Swift 下行为不同），
   **损失只有这几步**，而不是 7800 行 UI
3. P4 之后是纯 UI，风险低但耗时长——那时候你已经在用自己能跑的原生版了

**反过来，如果一次全上**：7800 行 UI 写完才发现启动层有问题，
那部分 UI 全部要跟着改接口。
