## 2. 真实障碍（**先纠正一个错判**）

### 2.1 本鱼一开始判错了

本鱼一度以为上游 `launcher.js` 的 `exec()` 会**阻塞** `launch()`。
**实测否定了这个判断**：

```js
exec(`"${nwjsPath}" "${gameFolder}"`, (err, stdout, stderr) => { ... })
//  ↑ exec 是异步的，函数立即返回；回调在进程退出后才触发
```

四个引擎（nwjs / mkxpz / easyrpg / renpy）**全部用 `exec`**，且都是
「调完就返回、不 await」。所以 `await launcher.launch()` **不会挂住**。

### 2.2 真正的问题：`exec` 不给进程句柄

`exec` 只回一个 `ChildProcess`（有 `.pid`），**但上游没把它传出来**：

```js
function launch(...) {
  exec(cmd, cb)     // ← 返回值被丢弃
}                   // ← launch() 返回 undefined
```

后果：
- 拿不到 PID
- 不知道游戏还在不在跑
- 无法关闭

**这才是「好用」的缺口。**

## 3. 方案：**在加载 launcher 时注入 `child_process`**（不碰上游、不重复启动）

### 3.1 核心思路

`core-host.ts` 的 `loadScript()` 用 `createRequire` 装载 launcher。
本鱼改成：**用 `Module` 手工编译，只对这一个模块劫持 `require('child_process')`**，
返回一个「自己的 exec」，它：

1. 用真正的 `spawn` 起进程（拿到 PID）
2. 登记到进程表（`gameId → { pid, startedAt, engine }`）
3. 保留原 `exec` 的回调语义（退出时调 callback）

**为什么这比改上游好**：

| 方案 | 问题 |
|---|---|
| 改 modules 仓库的 launcher.js | 上游一更新就被冲掉；且要改 4 个模块 |
| 自己 spawn 再调上游 | **会启动两次** |
| **注入 child_process**（本方案） | 零上游改动；launcher 以为自己调的是原生 `exec`，实际走我们的 |

### 3.2 可行性已验证

本鱼用两个最小实验证明：

**实验 1：全局劫持 `Module._load`** —— 成功，但**弃用**（影响全进程，太危险）

**实验 2：作用域劫持** —— 只用 `Module` 实例的 `require`，成功：

```
[scoped] 拦截到 child_process
[scoped] cmd = fake-game
pid 拿到: 999
```

**只影响那一个 launcher 模块，别的代码照常。**

### 3.3 实现要点

```ts
// core-host.ts
function loadScript(folder, relative, hooks?: { execInterceptor?: ExecInterceptor }) {
  const root = modulePath(folder)
  const file = scriptPath(root, relative)
  // 有 hook 时走手工编译（为了注入 child_process）
  if (hooks?.execInterceptor) {
    const m = new Module(file, null)   // Module 需要 require('module').Module
    m.filename = file
    m.paths = Module._nodeModulePaths(path.dirname(file))
    const originalRequire = m.require.bind(m)
    m.require = (id: string) => {
      if (id === 'child_process') return makePatchedChildProcess(hooks.execInterceptor)
      return originalRequire(id)
    }
    m._compile(fs.readFileSync(file, 'utf8'), file)
    return m.exports
  }
  // 无 hook 时保持原路径（createRequire），避免影响既有行为
  const cache = createRequire(pathToFileURL(file)).cache
  for (const key of Object.keys(cache)) if (key.startsWith(root + path.sep)) delete cache[key]
  return createRequire(pathToFileURL(file))(file)
}
```

### 3.4 `exec` 的替代实现

```ts
function makePatchedChildProcess(intercept: ExecInterceptor) {
  const real = require('child_process')
  return {
    ...real,   // execFile / spawn / execSync 等一律透传
    exec(command: string, optionsOrCb, maybeCb) {
      // 解析 callback（exec 支持 (cmd, cb) 与 (cmd, opts, cb)）
      const cb = typeof optionsOrCb === 'function' ? optionsOrCb : maybeCb
      const child = real.exec(command, optionsOrCb as never, ((err, stdout, stderr) => {
        intercept.onExit?.(err)
        cb?.(err, stdout, stderr)
      }) as never)
      // 关键：把 PID 交给上层
      intercept.onSpawn?.(child.pid ?? null, command)
      return child
    }
  }
}
```

**注意**：透传其余方法（`spawn`/`execFile`/`execSync`），只替换 `exec`——
这样即使上游某天改用 `spawn`，最坏是「失去进程追踪」，而不是崩。

## 4. 数据结构

### 4.1 主进程内（不落盘，运行时状态）

```ts
export interface RunningGame {
  gameId: string
  pid: number
  engine: string
  command: string
  startedAt: string
}

/** gameId → RunningGame */
const running = new Map<string, RunningGame>()
```

**为什么不落盘**：进程状态是**运行时事实**，重启应用后当然不成立。
落盘只会产生「显示正在运行但进程早就没了」的假象。

### 4.2 `Snapshot` 新增（只读投影）

```ts
export interface Snapshot {
  // …既有字段…
  /** M3.5：正在运行的游戏（运行时状态，不落盘）。 */
  running?: Array<{ gameId: string; pid: number; startedAt: string }>
}
```

### 4.3 游玩记录（**这个要落盘**）

```ts
// games.json 的 GameRecord **不改**（D10）
// 旁挂：library-meta.json 里加游玩字段？
```

**决策点**：放哪？

| 位置 | 问题 |
|---|---|
| `GameRecord` 加 `lastPlayedAt` / `playCount` | ⚠️ 违反 D10（上游 schema） |
| `library-meta.json` | ✅ 旁挂（同 D18 思路），但语义上「游玩记录」不是「元数据」 |
| **新增 `play-stats.json`** | ✅ 语义清晰、独立、可删 |

**本鱼选第三个**：`<dataDir>/play-stats.json`，结构：

```json

}
```

## 5. IPC 命令

| 命令 | 参数 | 返回 | 队列 |
|---|---|---|---|
| `runningGames` | — | `RunningGame[]` | **绕队列**（只读内存，毫秒级） |
| `stopGame` | `{ gameId }` | `{ ok, message }` | 进队列（可能等待进程退出） |

`launch` 成功后**顺便**记录：
- `running.set(gameId, {...})`
- `playStats.record(gameId, startedAt)` → 落盘
- 发 `gameStarted` 事件

进程退出时：
- `running.delete(gameId)`
- `playStats.finish(gameId, durationSeconds)`
- 发 `gameExited` 事件（带 exitCode）

## 6. 关闭游戏的实现

```ts
async function stopGame(gameId: string): Promise<{ ok: boolean }> {
  const entry = running.get(gameId)
  if (!entry) throw failure('error.gameNotRunning', 'Game is not running.', { id: gameId })

  // ① 先温和：SIGTERM（macOS 上 NW.js / mkxp-z 会走正常退出流程）
  process.kill(entry.pid, 'SIGTERM')
  // ② 给 5 秒体面退出
  const exited = await waitForExit(entry.pid, 5000)
  if (exited) return { ok: true, message: '已关闭' }
  // ③ 还在就强杀
  process.kill(entry.pid, 'SIGKILL')
  await waitForExit(entry.pid, 2000)
  return { ok: true, message: '已强制关闭' }
}
```

**注意**：`process.kill` 需要**同用户权限**——我们和游戏是同一个用户，没问题。

**风险**：如果 PID 被系统复用（游戏退出后那个号给了别的进程），`kill` 会杀掉无关进程。
**缓解**：退出监听里**立刻** `running.delete`，所以 `stopGame` 只能对「我们认为在跑」的进程动手；
且 SIGTERM 前再验一次进程是否还是那个可执行文件。

### 8.1 实施中与方案的偏差（都已如实落地）

| # | 方案原写 | 实际做法 | 原因 |
|---|---|---|---|
| ① | §4.1 `RunningGame` 只有 4 个字段 | 多了 `command` 与 `execPath` | PID 复用复核（§6/§9 R3）需要它——没有可执行路径就没法判断「这个号现在跑的是不是当初那个程序」 |
| ② | §3.1 `exec` 替代实现只写了 `onSpawn`/`onExit` | 另加 `child.once('exit')` + `child.once('error')` 兜底 | **上游可能根本不传回调**（`exec(cmd)` 单参形态），那 exec 的回调永远不来 → 进程表永远不注销 → UI 一直显示「运行中」 |
| ③ | §4.2 `Snapshot.running` 每项 `{gameId,pid,startedAt}` | 同上，**不带** `command`/`execPath` | 命令串里可能有用户本地路径，UI 用不到，没必要过桥（最小暴露面） |
| ④ | §5 `stopGame` 返回 `{ok,message}` | 返回 `{ok, action, messageKey}` | 主进程只给 i18n key，文案在渲染层（§3.9 的老规矩）；`action` 区分「温和退出」与「强杀」，UI 可以给不同措辞 |
| ⑤ | §7.1 只说「显示已运行 N 分钟」 | 时长文案走 `formatDuration`（秒/分钟/小时+分钟） | 一个刚启动的游戏显示「已运行 0 分钟」很奇怪；秒级更真实 |

### 8.2 探针实测（`node scripts/probe-m35.cjs`，本机 Windows）

探针不用真引擎（Windows 上没有 mac 二进制），而是造一个**假 mkxpz 模块**，
launcher.js 照上游真实形态写（`exec(cmd, cb)` 且**丢弃返回值**）——
这恰好是 M3.5 要修的那个形态。实测结果：

- `runningCount=1`、`runningPid=20100`、`hasRealPid=true` → **真的拿到 PID 了**（D48/D49 生效）
- `execPathParsed="ping"` → 从命令串正确抠出可执行文件（PID 复用复核的原料）
- `playStatsExists=true`、`playCount=1` → `play-stats.json` 真的落盘（D51）
- `snapshotHasRunning=true`、`snapshotRunningHasNoCommand=true` → S4 字段如约下发，且没漏 `command`
- **详情页**：`hasRunningBar=true`、`runningText="正在运行（已 0 秒）"`、`hasCloseButton=true`、`hasLaunchButton=false`
- **卡片**：`cardCount=1`、`runningDots=1`、`cardHasStopButton=false`（D41 的精神：卡片不给关闭按钮）
- **重复启动**：`relaunchRejected=true`，`decodeBridgeError` 拿到 `error.gameAlreadyRunning`，且 `playCountStillOne=true`
- **关闭**：`stopResult.action="terminated"`、**`processReallyGone=true`**（用系统层 `kill(pid,0)` 复核，不只是信我们自己的表）
- **关闭后**：`runningCountAfterStop=0`、详情页 `hasRunningBar=false` / `hasLaunchButton=true`（回到启动按钮）
- **停止一个没在跑的游戏**：`stopIdleRejected=true` + key 正确解回 `error.gameNotRunning`
- `consoleErrors=[]`、`finalHtmlLen=2982` → 全程没有组件白屏

**探针自己踩到的坑（值得记）**：
1. 第一版直接用 `window.tsumi.invoke('launch')` 启动，绕过了 Pinia store →
   页面读的是 store 里的 `running`（snapshot 的投影），所以 DOM 上什么都没变（显示「没有运行」）。
   **验收 UI 必须走 store**，否则验的是「IPC 能跑」而不是「用户点了按钮会看到什么」。
2. 假「游戏」原先写 `process.execPath -e "setTimeout(...)"` —— 那是 **Electron 的** execPath，
   带 `-e` 不干活，进程立刻退出（表现为 `runningCount=0` 一脸懵）。
   改成系统自带的 `ping -n 120 127.0.0.1`（win）/ `sleep 120`（其它），不依赖 node 在 PATH 上。
3. `executeJavaScript` 里写顶层 `await` → `Uncaught SyntaxError: await is only valid in async functions`。
   注入的代码必须包成 `(async () => { ... })()`。

## 9. 风险

| # | 风险 | 处置 |
|---|---|---|
| R1 | `Module` 手工编译与 `createRequire` 的行为差异 | **只在有 hook 时走手工编译**；无 hook 保持原路径。加测试对比两种装载 |
| R2 | 上游 launcher 可能用 `exec` 的同步变体（`execSync`） | 只替换 `exec`，其余透传；`execSync` 那条路径就是「追踪不到」，不崩 |
| R3 | PID 复用导致误杀 | 退出监听立即 `running.delete`；`stopGame` 前复核可执行文件 |
| R4 | NW.js 可能有子进程树（不止一个 PID） | 第一版只 kill 主 PID；若实测不干净，后续用 `pkill -P <pid>` 整棵树 |
| R5 | 游戏是用户从外部启动的（不经过我们） | **不管**。我们只追踪**自己启动**的进程，这是诚实的行为 |

## 10. 新增决策

| # | 决策 | 理由 |
|---|---|---|
| **D48** | 进程追踪用**「加载 launcher 时注入 `child_process`」**，不改上游 modules 仓库 | 上游一更新就会冲掉我们的改动；且要改 4 个模块。注入方案零上游改动，launcher 以为自己调的是原生 exec |
| **D49** | 注入**只替换 `exec`**，其余 `child_process` 方法原样透传 | 上游可能改实现；透传保证「最坏失去追踪」而不是崩溃 |
| **D50** | 进程状态**只在内存**，不落盘 | 进程是运行时事实；落盘会产生「显示在运行但进程早没了」的假象 |
| **D51** | 游玩记录（`lastPlayedAt`/`playCount`/`totalSeconds`）落**独立的 `play-stats.json`** | 不放 `GameRecord`（守 D10）；不放 `library-meta.json`（语义不同：那是 DLsite 元数据）。独立文件可单独删 |
| **D52** | `stopGame` 走 **SIGTERM → 等 5 秒 → SIGKILL** 两段式 | 温和优先（游戏可能要保存），但卡死时也要能救 |
