# 需求：「游戏内文本汉化」（暂不实现，只记录需求）

> **状态：需求记录，不是实施方案。** 用户 2026-11-04 明确：
> **「一个游戏对应一份翻译文件」**，且**当前先把 M2.6 做完**，汉化功能只做需求沉淀。
>
> 本文件的作用：将来真要开工时，不用再从头调研格式与可行性。
> **不包含任何第三方翻译内容**（样本仅用于分析结构，不入库）。

---

## 1. 需求一句话

**让用户能给游戏挂上一份「原文→译文」对照表，启动时游戏内文本显示为中文。**

不是自动翻译，是**用户提供翻译表，我们负责加载与注入**。

---

## 2. 关键前提（用户明确）

### 2.1 **一个游戏 = 一份翻译文件**，不是通用表

实测验证（用用户的真实样本对照两款游戏）：

| 游戏 | 与样本翻译表的命中率 |
|---|---|
| `Unholy_maiden` | **40.3%**（18714/46382） |
| 艾妮希雅 | **0.5%**（235/43769） |

**结论**：翻译表是**按作品定制的**，不同游戏的文本几乎不重叠。
所以设计上**必须按游戏存储**，不能做「全局一本字典」。

### 2.2 格式：平铺字典 `{ 原文: 译文 }`

实测样本结构（39,086 条，**零嵌套**、值全是 string）：

```json
{
  "ローズフォード市街 中央広場": "罗斯福德市街 中央广场",
  "鳩1": "鸽子1",
  "通行人": "行人",
  "ダミー": "假人"
}
```

**长文本也支持换行**（实测样本里有 5 行的描述文本，`\n` 原样保留）：

```
"第二層に広がる広大な毒沼\n「蟲毒の底」の最奥には..." : "在第二层蔓延的广阔毒沼，\n 「虫毒之底」的..."
```

### 2.3 这个格式是 MV/MZ 生态的通行做法

第三方工具 **RPGMakerUtils** 用的就是 `translations.json` + JS 插件注入，
它翻译的字段与真实 `data/System.json` 完全对得上（实测）：

```
currencyUnit / gameTitle / terms(basic,commands,params,messages) /
armorTypes / skillTypes / weaponTypes / elements / equipTypes / switches / variables
```

| # | 需求 | 优先级 | 说明 |

| T1 | **导入翻译文件** | 必做 | 用户选一个 JSON，我们校验格式并关联到某个游戏 |

## 4. 必须先想清楚的三个坑

### 4.1 改游戏目录 = 改用户文件 ⚠️

MV/MZ 的翻译插件注入要动 `js/plugins/`，可能还要改 `js/plugins.js` 或 `package.json`。
**这与我们「不修改游戏文件」的既往定位冲突**（M3 的 D34 明确不代劳 DRM 破解）。

**建议方案**：
- 注入前**强制备份**被改动的每个文件
- 提供「一键还原」
- **首次启用时明确告知**「这会修改游戏目录」，让用户确认

### 4.2 加密发行（`.rgss3a`）的游戏怎么办

Older RPG Maker（XP/VX/VX Ace）的文本在 `Data/*.rvdata*` 里，
可能是加密归档（M3 的 D34 已决定不解包）。

**MV/MZ（NW.js）的文本是明文 JSON**（实测：`data/System.json` 直接可读），
所以**第一版只支持 MV/MZ**，RGSS 系列明确不做。

### 4.3 翻译表的来源与授权 ⚠️

用户提供的那份 39k 条样本是**别人手工翻译的成果**。

**红线**：
- 我们**不内置任何第三方翻译内容**
- 用户自己导入的表，责任在用户
- 将来若做「共享翻译库」，必须先解决授权

## 5. 与现有架构的衔接点

| 位置 | 作用 |
|---|---|
| `src/main/` 新增 `translation.ts` | 校验格式 / 覆盖率统计 / 提取待翻译文本（纯逻辑，不 import electron） |
| 翻译表存储 | `<dataDir>/translations/<gameId>.json`（旁挂，**不动 `GameRecord`**，同 D18 的思路） |
| 注入 | 新增 IPC `applyTranslation` / `revertTranslation` |
| 引擎适配 | **只做 `nwjs`（MV/MZ）**；M1 的 `launcher.js` 已有 `copyCheatFiles` 先例，注入逻辑可参考（但那是上游代码，我们不动） |

## 6. 排期建议

**当前不做。** 顺序建议：

1. **M2.6**（海报墙与详情页重构）← **用户指定先做这个**
2. M4（存档管理 + Cheat/变速）
3. **翻译（本文件的需求）** ← 可以插在 M4 前后，取决于用户优先级

理由：翻译是**独立的新功能面**，改动量大（新文件 + 新 IPC + 注入机制 + UI），
不适合与其他里程碑并行。
