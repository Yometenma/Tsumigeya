## 2. 实测：四个引擎的存档位置（🔴 关键结论）

### 2.1 最要命的一条：**同一引擎，存档位置不同**

用户真机上两个 NW.js 游戏：

| 游戏 | 引擎版本 | 存档位置 | 后缀 |
|---|---|---|---|
| `Karryn's Prison` | **MV** | `<游戏>/www/save/` | `.rpgsave` |
| `艾妮希雅与契约纹…` | **MZ** | `<游戏>/save/` | `.rmmzsave` |

**原因**：MV 的工程根目录是 `www/`，MZ 取消了 `www/`（根目录直接就是工程）。

⇒ **绝不能按引擎硬编码一条路径**。判定顺序必须是：

```
① 有 <游戏>/www/save/     → MV 布局
② 有 <游戏>/save/         → MZ 布局
③ 两者都没有               → 还没存过档（目录可能不存在）
```

实测证据：

```
Karryn's Prison/www/save/   → config.rpgsave / file1.rpgsave / global.rpgsave
艾妮希雅…/save/              → config.rmmzsave
艾妮希雅…/package.json       → 存在，且**没有 www 子目录**（确认是 MZ）
```

### 2.2 MKXP-Z：**存档不在游戏目录里**

实测 `傭兵の冒険_CHN/` 顶层：

```
Audio/ Data/ Fonts/ Game.exe Game.ini Game.ini.tsumigeya-bak
Graphics/ System/ mkxp.json（v0.5.2 遗留，可删）
```

**没有 Save 目录，也没有 Save*.rvdata2**。
mkxp-z 自己的数据目录 `~/Library/Application Support/mkxp-z/` **是空的**。

**两个可能（无法只靠静态检查区分）**：

| 可能 | 判据 |
|---|---|
| **A**：用户还没玩到能存档的地方（新游戏根本没存过） | 最可能 —— 目录空着是因为**从没写过** |
| **B**：mkxp-z 把存档写到了别处（配置里的 savePath） | 但 `mkxp.json` 里**没有 save/savePath 相关键** |

⇒ **无法在纸上定案。实施第一步必须先让用户真存一次档，再看文件出现在哪。**

**这是本方案最重要的一条：M4 的第一件事不是写代码，是拿到一个真实存档样本。**

### 2.3 EasyRPG / Ren'Py

用户库里**没有这两个引擎的游戏**（5 个游戏：3 个 NW.js、1 个 MKXP-Z、1 个未登记）。

上游 manifest 的约定（未在本机验证）：

| 引擎 | 常见位置 |
|---|---|
| EasyRPG | `<游戏>/Save/`（`.lsd` 文件） |
| Ren'Py | `~/Library/RenPy/<游戏名>/`（mac 上，**不在游戏目录**） |

⇒ **实施时若允许用户添加这两种游戏，要用同样的「先找了再说」策略**，不要硬编码。

## 3. 方案

### 3.1 核心设计：**存档位置是「探测」出来的，不是「配置」出来的**

```ts
// src/shared/save-locate.ts（纯函数，可单测）
export interface SaveLocation {
  dir: string
  layout: 'mv' | 'mz' | 'mkxpz' | 'easyrpg' | 'renpy' | 'unknown'
  pattern: RegExp       // 哪些文件算存档
}

export function locateSaves(gamePath: string, engine: string): SaveLocation
```

**探测顺序**（每一步都要 `existsSync`，不能假设）：

```
engine === 'nwjs':
  ① <game>/www/save/ 存在 → { layout:'mv', pattern: /\.rpgsave$/ }
  ② <game>/save/ 存在     → { layout:'mz', pattern: /\.rmmzsave$/ }
  ③ 都没有 → 返回 null（UI 显示「还没有存档」）

engine === 'mkxpz':
  ① <game>/Save1.rvdata2 之类的直接文件 → 用游戏目录
  ② ~/Library/Application Support/mkxp-z/ 下有子目录 → 用那个
  ③ 都没有 → 提示「先玩到能存档的地方」

engine === 'easyrpg' : <game>/Save/
engine === 'renpy'   : ~/Library/RenPy/<title>/
```

**⚠️ 关键**：`③ 都没有` 必须能**区分「没存过」和「找不到」**——
前者要告诉用户「玩到存档点再来」，后者要能点「手动指定目录」。

### 3.2 只读优先（查看）

```ts
export interface SaveSlot {
  file: string          // 绝对路径
  name: string          // 文件名
  size: number
  mtime: string         // ISO
  kind: 'slot' | 'config' | 'global'   // 区分存档槽与配置文件
}
```

**`config.*` / `global.*` 是配置，不是存档槽** —— UI 里要分开列，
否则用户会以为是第 0 号存档。

### 3.3 备份 / 导出

**不做「备份到数据目录」**（那是隐形的第二份，用户找不到也没法带走）。
**只做「导出成一个包」**：

```
tsumigeya-save-<游戏名>-<YYYYMMDD-HHMM>.zip
  ├── manifest.json     { gameTitle, engine, exportedAt, layout, files:[{name,sha256}] }
  └── saves/            ← 原始文件，一个字节不改
```

**注意：不加工存档内容**（那是游戏的格式，我们不懂也不该改）。

### 3.4 「游戏正在运行」的保护

实测 `process-registry` 只在内存（D50），能查到某游戏是否在跑。

**规则**：游戏在跑时**只允许查看，禁止导出**，并明确提示「请先关闭游戏」。
理由：运行中的存档可能正在写，导出的包会是**半截文件**——用户带着它换机会丢档。

### 3.5 同步方案「预留」到什么程度

**只留接口，不实现**：

```ts
export interface SaveSyncProvider {
  id: string
  labelKey: string
  // 双向：拉下来 / 推上去
  pull(gameId: string, targetDir: string): Promise<void>
  push(gameId: string, sourceDir: string): Promise<void>
}
```

**设置页放一个「同步方案：无 / 手动导入导出」 的下拉**，选「无」是默认，
选「手动」时只是把导出/导入做顺一点。**不接任何云**（D31 的精神：绝不动用户的东西）。

## 4. 实施顺序

| 步 | 内容 | 前置条件 |
|---|---|---|
| **S0** | 🔴 **取得真实样本** | **用户必须先玩到能存档，把文件给我** |
| S1 | `shared/save-locate.ts` 纯函数 + 探测（用真实目录当 fixture） | S0 |
| S2 | 主进程 `save-list`（只读 IPC，走 `OFF_QUEUE_METHODS`） | S1 |
| S3 | 详情页「存档」区块：列表 + 「在访达中打开」 | S2 |
| S4 | 导出 zip（含 running 保护） | S3 |
| S5 | 导入（还原到探测到的目录，**先备份现有存档**） | S4 |
| S6 | 同步接口占位 + 设置页下拉 | S5 |

**S0 是硬闸门**：拿不到真实存档，S1 写出来的探测逻辑必然猜错布局（
MKXP-Z 那份连"在不在游戏目录"都还没确定）。

## 6. 不做的事（明确写出来，免得实施时扩大）

| 不做 | 理由 |
|---|---|
| ❌ 解析存档内容（改钱/改道具） | 那是作弊，不是存档管理；格式各版本不同，改了会坏档 |
| ❌ 云同步（Dropbox/iCloud/自建） | 要处理账号、冲突、隐私；且大多数人不需要 |
| ❌ 自动备份（定时往数据目录复制） | 用户找不到的第二份；要备份就让他明确导出 |
| ❌ 改游戏文件结构 | 存档是游戏的格式，一个字节都不动（只打包） |
