# 引擎范围扩展 · 实施方案

> 目标：把「能认、能跑」的 DLsite 引擎范围尽可能铺满，**全部自己实现**，不依赖上游模块仓库。
> 状态：**待用户拍板后实施**。本文是契约，不是进度记录。

---

## 1. 一句话结论

**分三层，只做前两层。**

| 层 | 形态 | 判定标准 | 本版本 |
|---|---|---|---|
| **L1 加载器** | 运行时是浏览器，游戏是网页目录 | 资源是 HTML5/JS | ✅ 做 |
| **L2 解释器** | 运行时读游戏数据文件 | 资源是数据，不是机器码 | ✅ 做 |
| **L3 兼容层** | 跑 Windows 二进制 | 只有 `.exe` | ❌ **不做**（用户 2026-11-05 拍板：交给 CrossOver） |

用户原话：「windows兼容的游戏有CrossOver嘛，不做也可以的」。

这条决策替换掉 AGENTS.md 里 D57 的隐含含义：**D57「未知引擎不回退」仍然有效，但「不支持」的措辞要改** ——
从「本版本支持：四个引擎」改成「这个引擎需要 Windows 兼容层（CrossOver 之类），Tsumigeya 不代跑」。

## 2. 现状：4 个引擎，两种形态

现有 4 个引擎其实是**同一个公式的两次应用**：

> **资源跨平台 + 有 macOS 运行时 ⇒ 自己实现，跟作者发不发 mac 版无关。**

| 引擎 | 资源 | 运行时 | 形态 |
|---|---|---|---|
| nwjs | `www/` 目录（JS+素材） | NW.js macOS | L1 |
| mkxpz | `Data/*.rxdata` | mkxp-z | L2 |
| easyrpg | `RPG_RT.ldb` | EasyRPG Player | L2 |
| renpy | `.rpy` + `game/` | Ren'Py SDK | L2 |

⚠️ **这条公式是本方案的唯一判据**。不要再拿「DLsite 上标注支持 Mac 多少部」当依据 ——
那个指标测的是作者出没出 mac 版，与本项目能不能跑完全无关（本鱼踩过这个坑）。

## 3. 各引擎清点（2026-11-05 实测）

数据源两个，口径不同，都注明：

- **[A] doujin-game.jp**（按「作り」分类的样本统计，约 5,300 部成人向同人游戏）
- **[B] dlcprice.com**（DLsite 官方 genre/ジャンル 作品数，更接近官方口径）

| 引擎 | 作品数 | 源 | 资源跨平台 | macOS 运行时 | 归属 |
|---|---|---|---|---|---|
| RPG Maker 全系列 | 4,367 [A] / **3,351** [B] genre 510 | A/B | ✅ | ✅ 已有 | **已支持** |
| **TyranoScript** | 351 [A] | A | ✅ HTML5 | ✅ 用 NW.js | **L1 · 做** |
| **吉里吉里** | 75 [A] | A | ✅ `data.xp3` | ✅ krkrsdl2 (MIT) | **L2 · 有条件** |
| Unity | 327 [A] | A | ❌ IL2CPP 平台锁定 | ➖ | L3 · 不做 |
| RPGBakin | **242** [B] genre 640 | B | ❌ **仅 Windows** | ❌ | L3 · 不做 |
| ウディタ（WOLF RPG Editor） | 169 [A] | A | ❌ | ❌ | L3 · 不做 |
| GameMaker / SMILE / SRPG Studio / LiveMaker / NScripter 等 | 零星 | — | ❌ 多为 Windows | ❌ | L3 · 不做 |

### 3.1 RPGBakin 的判决依据（官方原文）

[rpgbakin.com/en/faq](https://rpgbakin.com/en/faq)：

> "Is it available for Mac? **At this time, only the Windows version is available.**"
> "Can I create and export my work for mobile or consumer use? At this time, we can only produce works for the **PC**."

工具与导出作品的运行环境都是 `Windows 10 (64bit)`。**没有「资源独立于 Windows 二进制」这回事。**
→ 归 L3，不做。这 242 部走 CrossOver。

### 3.2 吉里吉里的那个坑（必须先知道）

[krkrsdl2 官方页](https://krkrsdl2.github.io/krkrsdl2/en/) **明写**：

> "Running **unmodified commercial games** using this project is **not supported**. Please use Wine or GameNative instead."

- 它是 **MIT**，有 **macOS 预编译包**（`krkrsdl2-macos.zip` / appbundle），命令行是 `krkrsdl2 /path/to/startup/directory`
- **技术上能跑**（未魔改的商业游戏它并不会检测并拒绝，只是**不承诺支持**）
- 但这是上游的明确立场，我们若把它当「官方支持的引擎」宣传，等于替上游承诺它不愿承诺的事

**处置建议**：做成「**实验性**」引擎 —— 在引擎页标「实验（上游不承诺商用游戏兼容）」，用户可装可用，
出问题时的提示文案写明这是上游限制。**是否接受这条，由用户最终拍板**（见 §8 待决）。

## 4. 架构改动：把「认得出」和「跑得动」拆开

这是本方案最重要的一条设计，直接决定「范围能不能铺满」。

### 4.1 现状

`src/main/engines/registry.ts` 的 `ENGINES` 同时承担三件事：

1. 引擎页「可安装」列表
2. 自动识别（`definitionsFromRegistry`）
3. `gameEngine` 字段的合法值（`ENGINE_FOLDERS`）

而 `src/main/launchers/index.ts` 的 `LAUNCHABLE_ENGINES` 单独管「能启动」。

### 4.2 问题

L3 那些引擎（Unity / ウディタ / RPGBakin…）我们**认得出、跑不动**。
若塞进 `ENGINES`，引擎页会把它们列成「可安装」→ 下载地址是空的 → 用户点了必然失败。
若完全不认，用户添加游戏时得到「未知引擎」→ 他无法知道这是「需要 Windows」还是「本程序坏了」。

**这两种都不对。** 用户要的是「范围尽可能广」，那么**识别范围应该铺满**，运行范围诚实留白。

### 4.3 方案：三份清单

| 清单 | 位置 | 内容 | 用途 |
|---|---|---|---|
| `ENGINES` | `engines/registry.ts` | 6 个（现有 4 + tyrano + kirikiri） | 可安装 + 可识别 + 可启动 |
| `DETECT_ONLY` | `engines/registry.ts`（新增） | Unity / ウディタ / RPGBakin / GameMaker / SMILE / SRPG / LiveMaker / NScripter | **只识别**，不进可安装列表 |
| `LAUNCHABLE_ENGINES` | `launchers/index.ts` | 6 个 | 分发表 |

识别时两张表**合并**参与打分（`definitionsFromRegistry` 要接受「可启动 + 仅识别」两部分）；
`ENGINE_FOLDERS` **只来自 `ENGINES`**（写进 `games.json` 的引擎值必须是我们真能跑的 ——
但 `DETECT_ONLY` 命中的结果也需要能落盘，见 §5.3）。

⚠️ **顺序问题**：`DETECT_ONLY` 的规则必须排在可启动引擎**之后**，且**更弱**。
强命中（`all_required: true`）永远压过打分命中，所以只要 Tyrano / 吉里吉里的规则是强命中，
就不会被 L3 那些弱规则抢走。这条要有单测（见 §7）。

## 5. 实施步骤

### S1 · 扩展 registry 与三份清单（不动启动链路）

- `engines/registry.ts`：新增 `tyrano` / `kirikiri` 两个 `EngineDefinition`；新增 `DETECT_ONLY` 常量
- `engines/types.ts`：`EngineDefinition` 加可选 `experimental?: true`（吉里吉里用）
- `engines/detect.ts`：`definitionsFromRegistry` 接受合并表（保持向后兼容的签名）
- `launchers/binary-paths.ts`：`ENGINE_IDS` 加 `'tyrano' | 'kirikiri'`
- **不写 launcher**（S3/S4 再写），先让识别与引擎页能跑

**验收**：添加一个 Tyrano 游戏目录 → 识别出 `tyrano`，引擎页多出两张卡。

### S2 · TyranoScript（L1 · 分两阶段）

#### S2-a · 目录形式（含 `index.html`）

- **autodetect**：`files: ['tyrano', 'data']`，`all_required: true`
  - 用两个**目录**当判据，不用 `index.html` —— 因为 `index.html` 在开发者本地项目里太常见，
    会误伤。`tyrano/` + `data/` 是 Tyrano 的标准骨架。
  - ⚠️ **不能和 nwjs 撞车**：nwjs 规则是 `['nw.dll','package.json']` 强命中。
    一个 Tyrano 的 NW 打包版可能同时有 `package.json`（在 `app.nw` 里面，不在根），
    所以根上同时出现 `nw.dll` + `tyrano/` 的概率极低。**但要实测确认**。
- **launch**：复用 NW.js 运行时，`args: [folder, ...]`，与 `nwjsPlan` 同形
- **前提**：游戏目录根必须有 `package.json`（含 `"main": "index.html"`）
  - 若没有 → 见 S2-b 的 shim 策略

#### S2-b · `app.nw` / 单 exe 形式（**风险最高，必须先实测**）

Tyrano 的 Windows 分发包有三种形态（[官方文章](https://shikemokumk.hateblo.jp/entry/2016/01/22/141350)）：

1. **未打包目录**：`tyranoscript.exe` + `game/`（内含 `index.html`、`tyrano/`、`data/`）← S2-a 覆盖
2. **`app.nw`**：项目目录打成 zip 后改名 `app.nw`，与 `tyranoscript.exe` 并排
3. **单文件 `game.exe`**：`copy /b tyranoscript.exe+app.nw game.exe` —— **zip 拼接在 exe 尾部**

形态 3 **最可能在实际游戏里最常见**，而它在游戏目录里**除了 exe 什么都没有**，靠文件名认不出引擎。

**处置**：`prepare()` 读 exe 尾部 → 找 ZIP 的 EOCD（`PK\x05\x06`）→ 定位 zip 起始偏移 →
**分块读**（绝不能整读进内存，游戏可能 3GB）→ 用 `fflate` 解到
`<dataDir>/modules/tyrano/extract/<gameId>/` → 那里就有完整的 `index.html` + `tyrano/` + `data/`。

- **不写游戏目录**（守 D53）
- 解包只做一次，用 `gameId + exe mtime/size` 做缓存键
- ⚠️ **这条必须先在真机样本上验通**再决定要不要进版本。**验不通就把形态 3 标「不支持」**

**i18n**：`engines.desc.tyrano` / `args.tyrano.*`（Tyrano 几乎无用户可调参数，最大可能是只有
`fullscreen` 一项 —— 与 nwjs 共用 `args.fullscreen`）

**存档**：Tyrano 的存档位置**待实测**（可能是 `<游戏>/save/`，也可能是浏览器 localStorage 模式）。
在实测前 `save-locate.ts` 返回 `null`（= 不知道在哪），**绝不猜**（D85 的教训）。

### S3 · 吉里吉里（L2 · 有条件，标实验）

- **autodetect**：`files: ['data.xp3']` 或 `extensions: ['xp3']`，`all_required: true`
  - ⚠️ 有些游戏把脚本放 `data.xp3`，有些用 `startup.tjs` + 散文件。两种都要认。
- **binary**：`binary-paths.ts` 加 `krkrsdl2BinaryPath()`
  - 布局：`<dataDir>/modules/kirikiri/deps/krkrsdl2/krkrsdl2.app/Contents/MacOS/krkrsdl2`
  - 或直放 `<dataDir>/modules/kirikiri/deps/krkrsdl2/krkrsdl2`（两种布局都认，照 `renpyBinaryPath` 的写法）
- **launch**：`args: [folder]`（官方用法就是 `krkrsdl2 <启动目录>`）
  - 有 `startup.tjs` 时直接给目录；否则**待实测**
- **dependencies**：`krkrsdl2` → `https://github.com/krkrsdl2/krkrsdl2/releases/download/latest/krkrsdl2-macos.zip`
  - ⚠️ `latest` 是浮动 tag，**建议 pin 到具体 commit/tag** 并在 registry 里写死版本号（照 D60 的精神）
  - 许可证 **MIT**：可捆绑，需在分发物里带 MIT 声明（与 GPL-3.0 兼容）
- **`experimental: true`**：引擎页显示「实验」，卡片上给出上游免责声明的一句话说明
- **存档**：KAG 约定是 `<游戏>/savedata/`，**待实测确认**

### S4 · 存档判据接入

`src/shared/save-locate.ts` 的 `switch (engine)` 加两个 case：

- `tyrano` → 待实测（占位返回 `null`，UI 显示 `unknown` 态）
- `kirikiri` → `savedata`（KAG 默认，待实测确认）

⚠️ **`location: null`（不知道在哪）与 `empty: true`（还没存档）必须分开** ——
这是 M4 的核心判据（`saveSectionView`），别在模板里另判一份。

### S5 · i18n 与 UI 文案

- `locales/zh-CN.json`：`engines.desc.tyrano` / `engines.desc.kirikiri`、`args.<引擎>.*`
- **`error.engineNotLaunchable` 必须改**：现在硬写了四个引擎名（[ipc.ts:972](src/main/ipc.ts:972)），
  而 `launchers/index.ts:10` 的注释早就说这句该来自 `LAUNCHABLE_ENGINES`。
  改成 `{supported}` 占位 + 用 `LAUNCHABLE_ENGINES` 拼，**同时补一句 L3 的解释**：
  「需要 Windows 兼容层（如 CrossOver）的游戏，Tsumigeya 不代跑」。

### S6 · 测试

见 §7。

## 6. 不改的东西（明确边界）

- ❌ **不碰用户游戏文件**（D53）——解包、写 shim 全部落在 `<dataDir>/`
- ❌ **不做 WINE 类兼容层**（用户拍板）
- ❌ **不做「自动下载游戏」**——本项目是启动器，不是商店客户端
- ❌ **不为了凑数量加「只能认不能跑」的引擎到可安装列表**——那是「留着不起作用的开关」
  （D60 的同一个教训：比不显示更糟）

## 9. 覆盖率的诚实说法

在**明确归属引擎**的样本里（约 5,300 部）：

| 阶段 | 能跑 | 占归属样本 |
|---|---|---|
| 现在（4 引擎） | ~4,367 | **≈ 82%** |
| + Tyrano（S2） | ~4,718 | **≈ 89%** |
| + 吉里吉里（S3） | ~4,793 | **≈ 90%** |

剩下 ~10%（Unity 327 / Bakin 242 / ウディタ 169 等）**需要 CrossOver** —— 这是用户拍板的边界，
不是遗漏。**识别范围则铺到全部**（`DETECT_ONLY` 让用户添加这些游戏时得到准确说明而非「未知引擎」）。

⚠️ **这些百分比的分母是「按引擎分类的样本」，不是 DLsite 全站**（全站还有素材、音声、
漫画等非游戏品类，以及未被任何统计站收录的游戏）。引用时必须带这个限定。

## 10. 全量调研结论（2026-11-05 核实）

> 本节是**调研结果**，不是决策。采纳哪几条由用户拍板。

### 10.1 确定可做（判据 A+B 都成立）

| 引擎 | 运行时 | 许可证 | macOS 情况 | launcher 成本 |
|---|---|---|---|---|
| **NScripter** | ONScripter | **GPL-2+**（「或更高版本」→ **与 GPL-3.0 兼容**，已核实 Debian 版权文件） | tmkk 版有 **Apple Silicon 原生**二进制；insani 分支专为现代 macOS 构建 | 低（`onscripter <gameDir>`） |
| **RealLive**（Key 系） | rlvm | **GPL-3.0**（同许可） | 仓库明写 "for Linux and OSX" | 低 |
| **Godot（仅 GDScript 项目）** | Godot 编辑器二进制 | MIT | 官方 universal 二进制 | **中**（见 §10.3 的坑） |
| **TyranoScript** | 已做 | — | v4=NW.js / v5=Electron | 已做 |

### 10.2 需先验证再做

| 引擎 | 运行时 | 阻塞点 |
|---|---|---|
| **GameMaker** | Butterscotch（VM 模式 `data.win`） | 有 macOS arm64/x86_64 预编译；但**许可证是 AGPL-3.0**（不是 MIT/GPL）→ 对 GPL-3.0 项目有传导义务，只能「独立进程调用」分发。且**必须先判 VM vs YYC**（YYC 是原生机器码，直接出局） |
| **Pixel Game Maker MV** | 官方 player 仓库 `GGGweb-adm/PGMMV`（MIT） | 底层 cocos2d-x 3.17.1，仓库里有 `proj.ios_mac` 工程，但**无预编译 mac 包**，要自己编 cocos2d-x → 成本高（等于自造运行时） |

### 10.3 Godot 的三个硬事实（决定了要不要做）

1. **运行时体积**：`Godot_v4.6.1-stable_macos.universal.zip` ≈ **154 MiB**（universal 双架构）。C# 版 182 MiB。不是「再加 131MB」的量级，但也不小。
2. **能直接跑游戏**：给 `--main-pack` 就直接进游戏，**不弹编辑器、不要授权**（官方 issue #3593 里 akien-mga 原话）。
3. **⚠️ 4.6 起 `--main-pack` 在 export template 里被默认禁用**（PR #111909）。实测 4.6.2 报 `compiled without support for path overrides. Aborting.`，4.5.2 正常（issue #119376）。
   → 两条路：**(a)** 用编辑器二进制当 runner（154MB，无需自编译）；**(b)** 自编译 template 加 `disable_path_overrides=no`，或**锁 4.5.x**。

**pck 跨平台性的准确表述**（这是官方文档 + 社区实证都支持的）：
> Windows 版导出的 pck **能被 macOS Godot 加载** —— 前提是 **GDScript 项目 + 不用 GDExtension + 引擎版本匹配**。
> **C# 项目基本没戏**（issue #72159 实测报 `class could not be found` / `Failed to load hostfxr`）。
> 桌面↔桌面不受 VRAM 压缩纹理差异影响（都走 S3TC/BPTC）。

### 10.4 确定不做（原因逐条写清，不是「不可行」四个字）

| 引擎 | 不做的真实原因 |
|---|---|
| **SRPG Studio** | **Windows 原生 host + Windows 内置 JScript 5.8**（不是 NW.js！网上二手文档写错了）。无任何运行时重实现，重写等于从零造引擎 |
| **WOLF RPG Editor** | `Game.exe` 是闭源 DxLib 引擎；`Data.wolf` 有社区解析器（WolfTL/WolfDec）**但没有任何运行时重实现**。官方推荐的「ブラウザウディタ」方向是 Web 不是 mac 原生 |
| **SMILE GAME BUILDER** | 发行版 `player.exe` + `data.sgbpack`（加密包），**无公开运行时**。Unity Exporter 是**作者侧付费 DLC**，启动器无法替已发行游戏转换 |
| **RPG Developer Bakin** | 官方 FAQ：「created work 的运行环境和工具相同」+「only the PC」；Roadmap 的多平台导出**仍只是计划**。引擎是 Unity+C#，发行包 `.rbpack` 只有解包器 |
| **RPG Maker Unite** | 作者能出 Mac 构建，但那要**用 Unity 重新导出**；用户手上是编译产物 → 不可行。已从 Steam 下架 → 归 D88 DETECT_ONLY |

**Live2D 不是引擎**：纯表现层 SDK（读 `.moc3`），DLsite 上标 Live2D 的作品实际跑在 Tyrano/Unity/自研上。
→ 只能作为**识别特征**（`.moc3`、`live2d/` 目录）挂在宿主引擎上，**不建独立条目**。

### 10.5 吉里吉里 2 vs Z（对已做实现的确认）

- krkrsdl2 官方原话：「a port of **Kirikiri Z** ... **Based on Kirikiri 2 and Kirikiri Z**」，源码取自 krkr2 + krkrz 的 `dev_multi_platform` 分支。
- → **不需要为吉里吉里 2 另找运行时**，krkrsdl2 同时覆盖 2 与 Z，`data.xp3` 直接可读。
- **建议改用 `krkrsdl2-macos-appbundle.zip`**（官方另有 appbundle 产物）：对 Electron 启动器更省事，符合「引擎=目录」模型。当前实现已优先找 app bundle，方向一致。
- ⚠️ **arm64 未核实**：GitHub Actions 产物未标注架构，需在 mac 上 `lipo -info` / `file` 验一次。
- 许可证：`src/` 是 MIT → 与 GPL-3.0 兼容。上游「不承诺商用游戏兼容」的声明照旧（D90 的「实验性」标注依然准确）。

### 10.6 ⚠️ 已做 tyrano 的一个真实缺口（本轮新发现）

当前 `tyrano` 的 autodetect 是 `files: ['tyrano', 'data'], all_required: true`（相对游戏目录）。
它**只覆盖 Tyrano v4 的未打包形态**：

| 形态 | 目录结构 | 当前规则命中？ |
|---|---|---|
| v4 未打包 | `tyrano/` + `data/` 在游戏根 | ✅ |
| **v5 unpacked** | `resources/app/{index.html,main.js,tyrano/,data/}` | ❌ **深了一层** |
| **v5 packed** | `resources/app.asar` | ❌ 完全不命中 |

**判定特征（可直接进 detect.ts）**：
- v4：`ffmpegsumo.dll` + `nw.pak`
- v5 unpacked：`resources/app/{index.html,main.js,tyrano/}`
- v5 packed：`resources/app.asar`

**处置**：`import-target.ts` 的 MAX_ASCEND=2 让「选 `resources/app/index.html` 再退一层」能命中，
但**依赖用户恰好选对文件**，很脆弱。应补规则，而不是靠上退兜底。
（真机样本缺失前，这条记为待修，不假装已覆盖。）

### 10.7 其余 VN 引擎（2026-11-05 核实）

### 10.8 GameMaker 的判据（可升级为「可做」）

**纯本地判定 VM vs YYC**（不用跑游戏）—— 读 `data.win` 的 chunk 表：

| 情况 | 判定 | 依据 |
|---|---|---|
| 有 `CODE` chunk 且非空（含指针列表 + `nBytecodeOffset`） | **VM** ✅ 能跑 | 「bytecode is stored inside the `CODE` chunk，essentially just a pointer list」 |
| `CODE`/`FUNC`/`VARI` 为空 | **YYC**（旧 bytecode） ❌ | 「CODE, FUNC and VARI used to be empty」 |
| `CODE`/`FUNC`/`VARI` 完全缺失 | **YYC**（bytecode 17+） ❌ | 「entirely missing for bytecode 17」 |

判据落地：① 校验 `FORM` 头 → ② 遍历 chunk 找 `CODE` → ③ 长度 > 头 = VM，只剩头 = YYC，找不到 = YYC → ④ 比 WAD 版本是否在 **v8–v17**（Butterscotch 支持范围）。
另需排除：**GMRT**（新运行时，原生码）、**WAD v8 之前**、以及用了**非 FMOD 的外部扩展**。

**⚠️ 许可证建议（重要）**：Butterscotch 是 **AGPL-3.0**，对 GPL-3.0 项目有传导义务。
→ **把「判定」与「运行」拆成两套依赖**：判定用 **LibGM（GPL-3.0-only，可直接进仓库）**，运行才调**外部的** Butterscotch 可执行文件（独立进程调用，非链接）。

### 10.9 Launcher 复杂度与存档可控性（排期依据）

| 引擎 | 启动命令 | prepare 步骤 | 存档位置 | 能否纳入现有存档管理 |
|---|---|---|---|---|
| **Godot** | `Godot.app/Contents/MacOS/Godot --main-pack <abs path>` | 无（但**要解 pck 读 project_name**） | `~/Library/Application Support/Godot/app_userdata/<project_name>`（有 `use_custom_user_dir` 变体） | ⚠️ **半可**：能定位，但路径由工程决定、**无 CLI 参数可改**；且官方明确**导出工程不支持 self-contained 重定向** |
| **GameMaker** | `butterscotch /abs/path/data.win` | 无 | 有 **`--save-folder <dir>`** 可指定 | ✅ **可**（四者里唯一原生支持指定存档目录） |
| **NScripter** | `onscripter-en [--save=<dir>] [--scale]`，选项也可写 `ons.cfg` | **3 件**：① 必须有 `default.ttf`（否则**启动不了**）② 写 `game.id`（否则**存档进随机命名目录**）③ 可选 `ons.cfg` | 默认 Windows `C:\ProgramData\` / Linux `~/` 下按 `game.id` 命名的子目录；**可 `save=` 改** | ✅ **可**（`save=` / `--save=`） |
| **RealLive** | `rlvm <abs game dir>`（缺字体加 `--font`） | 1 件：字体 `msgothic.ttc` | ❌ **未查到** | ⚠️ **未知，须实测** |

**⚠️ 四条必须写进代码的坑**：
1. **Butterscotch 用相对路径且与二进制不同目录时会崩**（issue #93）→ **一律传绝对路径**
2. **ONScripter 缺 `default.ttf` 直接起不来**（不是警告，是起不来）
3. **ONScripter 缺 `game.id` 会把存档丢进随机命名目录** → 必须在 prepare 里写
4. **Godot 要解 pck 读 `application/config/name`** 才能定位存档目录

### 10.10 仍未核实（诚实清单，不编）

1. `xsystem4` 的许可证全文
2. `FelineSystem2` 的许可证 + mac 构建可行性
3. `rlvm` 的许可证、macOS 存档路径、arm64 支持
4. `ONScripter-EN`（fork）的许可证（**本体已知 GPL-2+**，见下）
5. Butterscotch 不给 `--save-folder` 时的默认存档路径
6. `krkrsdl2` 预编译产物是否含 arm64（需在 mac 上 `lipo -info` 验）
7. TyranoScript 的「License: Other」具体条款

**✅ 其中一条本鱼已自行核实并修正了研究员的说法**：
ONScripter 本体不是 `GPL-2.0-only`，而是 **`GPL-2+`（「or (at your option) any later version」）**。
依据：Debian 官方版权文件 `tracker.debian.org/.../onscripter/copyright-20230825-1` 明写
`License: GPL-2+`，正文含「either version 2 of the License, **or (at your option) any later version**」。
→ **`GPL-2+` 允许按 GPL-3.0 使用，因此与本项目（GPL-3.0）兼容**，不构成障碍。
（研究员说的「GPLv2-only 与 GPLv3 不兼容」在**普通法理上是对的**，但**这个包的许可证是 `+` 版**，所以结论反过来。）
