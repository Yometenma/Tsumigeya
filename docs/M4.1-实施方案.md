# M4.1 实施方案：自己维护引擎清单（彻底不再依赖上游模块仓库）

> **状态：待实施。**
>
> 用户 2026-04-07（会话内）：**「第一个现在很少有人用flash了，第二本身就是用来在macos上玩这些游戏的，
> 专门还装一个macos的引擎没必要，第三windows游戏暂时我有CrossOver」**
> → 那三个模块（ruffle / wine / macos）**不要了**。
>
> 随后用户更明确：**「都说不能要了……为什么还要自作主张留着」**、
> **「为什么是过滤，为什么是隐藏？为什么不是直接删掉」**、
> **「我们不是已经有了自己实现的4个源了吗，为啥还需要从上游拉取模块列表」**
>
> 结论：**不是从界面过滤，是让那三个在代码里彻底不存在；也不再从上游拉清单。**
>
> 基线：M1–M4.0 全绿（634 tests / 27 files），v0.4.0 已发布。

---

## 1. 现在到底依赖上游什么

M4.0 之后，启动逻辑是自己的（`src/main/launchers/`），**但引擎清单还从上游拉**：

```
自己的：launcher.js  ✗ 已不用（上游 542 行全是附加功能）
自己的：spawn 启动   ✓ src/main/launchers/
上游的：manifest.json ✓ 还在用 ← 本次要消灭的就是它
```

`manifest.json` 提供三样东西：

| 字段 | 用途 | 体量（实测） |
|---|---|---|
| `autodetect` | 怎么认这个游戏 | **4–10 行**，很小 |
| `gameArgs` | 参数表单 | nwjs 4 / renpy 2 / easyrpg 51 / **mkxpz 59** |
| `dependencies` | 二进制下载地址 | nwjs 6 / mkxpz 4 / easyrpg 2 / renpy 1 |

### 1.1 四个引擎的实测清单（2026-04-07 拉取）

### 1.2 一个必须修的隐患

**mkxpz 的 manifest 里硬编码了 xenolauncher 路径**（D58 切换后我们已不用那个目录）：

```
preloadScript = ["~/Library/Application Support/xenolauncher/modules/mkxpz/deps/kawariki/kawariki/preload.rb"]
midiSoundFont = "~/Library/Application Support/xenolauncher/modules/mkxpz/deps/soundfont/gmgsx-plus.sf2"
```

**自己维护清单时必须换掉**，否则 MKXP-Z 去读一个不存在的文件（D58 后 `xenolauncher` 目录已废弃）。

## 2. 方案：`src/main/engines/registry.ts`（4 个引擎的硬编码定义）

### 2.1 结构

```
src/main/engines/
├── registry.ts      ← ★ 唯一来源：4 个引擎的完整定义
├── types.ts         ← EngineDefinition（autodetect / gameArgs / dependencies）
└── （不建子文件，4 个引擎都写在 registry.ts 里，一起看更清楚）
```

**为什么 4 个都写在一个文件**：总共约 200–300 行，分散成 4 个文件反而要来回跳。且「有哪些引擎」一眼可见 —— 这正是删干净的意义。

### 2.2 类型

```ts
export interface EngineDependency {
  /** 下载地址（按架构区分，不区分则用 universal）。 */
  builds: { universal?: string; arm64?: string; x86_64?: string }
  /** 下载后是否解压（`.zip` 需要，`.sf2` 不需要）。 */
  unzip?: boolean
  /** 解压后是否剥掉与依赖名同名的那层（沿用 `installDependencies` 的规则，见已知坑）。 */
  stripSameNameLayer?: boolean
}

export interface EngineArgSpec {
  type: 'boolean' | 'int' | 'float' | 'string' | 'array' | 'dropdown' | 'multi-version'
  default: unknown
  title?: string
  options?: Array<{ value: string; label: string }>
}

export interface EngineDefinition {
  /** 模块目录名，也是 `gameEngine` 的值。 */
  folder: string
  /** 展示名。 */
  name: string
  /** 硬编码的版本（上游发新版时手动改这里）。 */
  version: string
  /** 一句话说明（引擎页展示）。 */
  description: string
  /** 怎么认这个游戏。 */
  autodetect: { files?: string[]; extensions?: string[]; all_required?: boolean }
  /** 参数表单（**只保留用户真会改的**，见 §3）。 */
  gameArgs: Record<string, EngineArgSpec>
  /** 二进制与资源下载。 */
  dependencies: Record<string, EngineDependency>
}

/** ★ 唯一来源。那三个（ruffle / wine / macos）在这里**不存在**。 */
export const ENGINES: readonly EngineDefinition[] = [nwjs, mkxpz, easyrpg, renpy]
```

### 2.3 4 个引擎的关键参数（**本次大幅精简**）

| 引擎 | 上游 | **我们保留** | 保留哪些 |
|---|---|---|---|
| **nwjs** | 4 | **2** | `version`（必填，决定用哪个 deps 版本）、`cheat`（默认 false） |
| **mkxpz** | 59 | **~10** | `rgssVersion` / `fullscreen` / `RTP` / `windowTitle` / `vsync` / `fontSub` / `preloadScript` / `midiSoundFont` / `defScreenW` / `defScreenH` |
| **easyrpg** | 51 | **~6** | `encoding` / `language` / `rtpPath` / `soundfontPath` / `vsync` / `showFps` |
| **renpy** | 2 | **2** | `command` / （存档目录自动算） |

**为什么砍这么多**：

- mkxpz 那 59 个里，`smoothScaling` / `xbrzScalingFactor` / `bicubicSharpness` 等 40 多个是**渲染画质微调**，
  普通用户根本不会碰。默认值就能玩，摆出来只会让人困惑。
- **砍掉不等于丢功能**：这些参数在 `mkxp.json` 里不写就用 MKXP-Z 自己的默认值，
  而上游给的那份默认值本来也是 MKXP-Z 的默认值（不是上游调的）。
- easyrpg 那 27 个 string 参数里，`loadGameId` / `recordInput` / `replayInput` / `battleTest` 等是调试用途。

> **投反对意见前先看这个**：如果将来需要某个参数，从本文件里加回来是一行的事（有注释指向上游原名）。

### 2.4 修正 xenolauncher 硬编码（§1.2）

```ts
// mkxpz 的默认值：用**运行时数据目录**，不写死
preloadScript: { type: 'array', default: ['<dataDir>/deps/kawariki/kawariki/preload.rb'] }
midiSoundFont:  { type: 'string', default: '<dataDir>/deps/soundfont/gmgsx-plus.sf2' }
//                            ↑ 启动时把 <dataDir> 替换成真实路径（mkxpz.ts 已有 prepare 阶段）
```

## 3. 上游依赖怎么处理

### 3.1 「不再从上游拉清单」

| 现在 | 改成 |
|---|---|
| `core.fetchRemoteManifestsList()` 拉 7 个模块的 manifest | **删掉**，改读 `src/main/engines/registry.ts` |

**连带影响**：

| 位置 | 改动 |
|---|---|
| `ipc.ts` 的 `remoteModules` 命令 | 改成返回 `ENGINES`（4 个硬编码定义） |
| `ipc.ts` 的 `checkEngineUpdates` | **删掉远程检查**（没远程清单了），改成「与硬编码版本对比本地已装版本」 |
| `EnginesPage` 的「可安装」列表 | 来自 `ENGINES`，**天生只有 4 个** |
| `engines.remoteError` / `loadingRemote` | 相关状态可删 |

### 3.2 `module.js` 怎么处理（**关键取舍**）

**保留**，但只保留「下载 + 解压 + 装到 deps/」的能力：

```
自己的 ENGINES（4 个硬编码）
        ↓  喂给它
module.js 的 installDependencies / extractArchive
        ↓
   <dataDir>/modules/<引擎>/deps/…
```

**理由**：那套下载/解压/事务回滚有 **68 个测试**（M3 写的），重写等于推倒重来，且它本身不依赖上游清单（吃的是我们传进去的 `wanted` 数组）。

> 也就是说：**删的是「引擎清单来自上游」，不是「下载能力」。**

### 3.3 `version-script` 怎么办

nwjs 有 `multi-version` 类型参数（要列 deps 目录下已装的版本）。这个走 `loadScript(folder, 'version-script')` —— **但上游的 `version-script` 也来自模块目录**。

**决定**：自己实现。它要做的事很简单 —— 扫 `<dataDir>/modules/nwjs/deps/version/` 下有哪些子目录。

## 4. 改动清单

| 文件 | 动作 |
|---|---|
| `src/main/engines/registry.ts` | **新增**（4 个引擎完整定义） |
| `src/main/engines/types.ts` | **新增** |
| `src/main/ipc.ts` | `remoteModules` → 返回 `ENGINES`；`checkEngineUpdates` 去掉远程拉取；删 `fetchRemoteManifestsList` 调用 |
| `src/main/core-host.ts` | `fetchRemoteManifestsList` / `fetchModulesForAutodetect` **删除或改成读 registry**；`readLocalManifests` 改成读 `<dataDir>/modules/*/manifest.json`（我们**自己生成**的 manifest） |
| `src/main/core-host.ts` 的 `detectFolder` | 用 registry 的 autodetect（不再靠远程 manifest） |
| `src/renderer/src/pages/EnginesPage.vue` | 删掉 `LAUNCHABLE_ENGINE_IDS` 镜像与标灰（**天生只有 4 个**） |
| `src/renderer/src/stores/engines.ts` | `remoteModules` 语义变化（改为「可安装的 4 个」） |
| `test/launchable-engines-consistency.test.ts` | **删除**（没有两份名单了） |
| `docs/打包与分发.md` 等 | 提「7 个模块」的地方改「4 个引擎」 |

### 4.1 重要：安装时**生成**自己的 manifest

`module.js` 的 `installModuleWithProgress` 会把远程 manifest 写进 `<dataDir>/modules/<引擎>/manifest.json`。
现在没有远程 manifest 了，改成：**安装时从 `ENGINES` 写一份我们的 manifest 进那个目录**。

这样：
- `readLocalManifests()` 照常能读（它读的就是那个文件）
- 上游的 `module.js` 逻辑不用动
- **格式与上游兼容**（万一用户也装原版 Xenolauncher，我们生成的 manifest 它能读）

## 5. 实施顺序

| 步 | 内容 | 验收 |
|---|---|---|
| **S1** | `engines/types.ts` + `registry.ts`（4 个引擎，参数精简版） | 单测：4 个引擎齐全、三个不支持的**不存在**、autodetect 规则与上游一致 |
| **S2** | `ipc.ts` 的 `remoteModules` / `checkEngineUpdates` 改读 registry | 单测：返回 4 个；不含 ruffle/wine/macos |
| **S3** | `detectFolder` / `readLocalManifests` 改读 registry + 安装时生成 manifest | 单测：四个引擎的自动识别仍正确（用现有 fixtures） |
| **S4** | 渲染层清理（删镜像、删标灰、`EnginesPage` 简化） | 端到端探针：引擎页只有 4 个 |
| **S5** | 删 `fetchRemoteManifestsList` 相关代码 + 删一致性测试 | 三绿；grep 确认无 `fetchRemoteManifestsList` 残留 |
| **S6** | i18n + AGENTS.md（D60–D62）+ 发版 | 全绿 |

## 6. 风险

| # | 风险 | 处置 |
|---|---|---|
| **R1** | 硬编码的下载地址失效（上游换了 release 文件） | 地址全在 `registry.ts`，改一处；失败时给可读错误 + 指向 GitHub 页面 |
| **R2** | 引擎版本过时（上游发了新版 nwjs） | 显式接受（用户拍板）。加注释说明「怎么升级」：改 `version` + 改 `dependencies.version/vX` 的地址 |
| **R3** | 精简参数后某些游戏玩不了（比如需要某个渲染参数） | 参数在 registry 里加回是一行的事；`mkxp.json` 不写就用 MKXP-Z 默认值（与上游等价，见 §2.3） |
| **R4** | 生成的 manifest 与上游格式不兼容 → 原版 Xenolauncher 读不了 | **照抄上游格式字段名**；S3 有测试断言生成的 manifest 能被 `readLocalManifests` 读回 |
| **R5** | 用户已装的模块（旧 manifest 来自上游）与新 registry 不一致 | 版本对比用 registry 的 `version`；不一致时提示「更新」（沿用现有逻辑） |

## 7. 新增决策

| # | 决策 | 理由 |
|---|---|---|
| **D60** | **引擎清单自己维护**（`src/main/engines/registry.ts` 硬编码 4 个），**不再从上游模块仓库拉 manifest**；ruffle / wine / macos 在代码里**不存在** | 用户明确不要那三个。过滤/隐藏只是障眼法（每次启动仍拉 7 个、代码里仍留着名字）；从源头删掉才是真的删。代价是引擎版本要自己维护（显式接受） |
| **D61** | 参数表单**大幅精简**（nwjs 4→2、mkxpz 59→约10、easyrpg 51→约6） | 砍掉的是渲染画质微调与调试参数，普通用户不碰；不写进 `mkxp.json` 就用 MKXP-Z 自己的默认值，**功能不丢**。需要时加回是一行 |
| **D62** | 安装引擎时**从 registry 生成** `<dataDir>/modules/<引擎>/manifest.json`（格式与上游兼容） | `module.js` 的 `readLocalManifests` 与 `installModuleWithProgress` 都读/写这个文件；没有远程 manifest 后必须自己生成。保持字段名兼容，原版 Xenolauncher 也能读 |
