# 竞品功能对照表（MTool / RPGMakerUtils）

> **性质**：调研记录，不是实施方案。用于判断「哪些功能值得排进路线图」。
> 采集时间 2026-11-04，样本由用户提供，均为 Windows 平台的第三方工具。
> **本文件不包含任何第三方代码**，只记录「它们做了什么」与「我们的判断」。

---

## 0. 两个样本是什么

| 工具 | 形态 | 源码可见度 | 定位 |
|---|---|---|---|
| **MTool** | NW.js 应用（153MB，含 node_modules） | ❌ 核心逻辑加密（`data/` 全是数字文件名 + `loader.bin`） | 一体化游戏汉化/启动/作弊工具 |
| **RPGMakerUtils** | .NET WPF（1.7MB） | ⚠️ 二进制但字符串清晰（88 条 ASCII 全暴露控件名） | 专注 RPG Maker 的字体/翻译/作弊工具 |

> **对 Tsumigeya 的意义**：不是拿来抄代码（一个加密、一个是 .NET），
> 而是**验证功能方向**——尤其「日本游戏的编码/字体问题是不是普遍痛点」。

## 1. MTool 的功能面（从目录结构与配置推断）

| 证据 | 推断功能 |
|---|---|
| `loaders/BakinLauncher.exe`、`BakinPlayerWrapper.exe` | 支持 **Bakin**（另一款日本 RPG 引擎） |
| `loaders/JoyCon2Mapper.exe` | **手柄映射**（Joy-Con） |
| `loaders/PIDDLLInject64.exe` | **DLL 注入**（作弊/汉化的实现手段） |
| `loaders/MToolWinlatorFilePicker.exe`、`MToolWinlatorProcProbe.exe` | **Winlator**（Android 跑 Windows 程序）集成 |
| `loaders/fontSetting.exe` | **独立字体设置程序**（不是内嵌功能） |
| `www/rawres/LangTL.json` | **界面多语言**（ja/EN/CHS 三套），含 `supportUrl` 指向自己的更新服务 |
| `www/rawres/trans1px.png` | **翻译渲染方案**（1px 图，推测用于测量/占位） |
| `node_modules/legacy-encoding` | **GBK / Shift-JIS 编码转换** |
| `node_modules/pe-library` + `resedit` | **PE 文件资源编辑**（改 exe 的字形/图标） |
| `data/` 加密 + `loader.bin` | 核心逻辑**故意保护**，防止被分析 |

**配置里的关键线索**：

```json
"searchingGame": "ゲーム接続を待機中",     ← 等待「游戏连接」（说明要挂钩运行中的游戏）
"trsLoading": "リソースを読み込み中..."     ← 从游戏里读文本
"defEngine": "TrsNT"                      ← 翻译引擎代号
```

**结论**：MTool 是**运行时注入型**——先把 DLL 注入游戏进程，再从内存/资源里抓文本，
翻译结果回填到渲染层。**不是静态改写文件**。

## 2. RPGMakerUtils 的功能面（88 条 ASCII 字符串完整暴露）

**六个界面模块**（`component/views/*.xaml`）：

| 模块 | 文件名 | 功能 |
|---|---|---|
| 作弊 | `addcheatusercontrol` | 金币 / 物品 / 技能（见下方字段） |
| **字体编辑** | `editfontusercontrol` | 改游戏字体 |
| **翻译** | `translateusercontrol` | 文本汉化 |
| 导入 | `importusercontrol` | 导入 `translations.json` |
| 密码搜索 | `searchpasswordusercontrol` | 「密码」搜索（未确认具体含义） |
| 关于 | `aboutusercontrol` | — |

**翻译模块的完整证据链**：

```
translations.json              ← 翻译数据文件
JtJsonTranslationManager.js    ← 翻译管理器（**JS 脚本，注入进游戏**）
TranslationPluginPath          ← 插件路径
GamePluginsJsPath              ← 游戏 plugins 目录（= MV/MZ 的 js/plugins/）
TargetJsonPath / TranslateJsonPath ← 源/目标 JSON
```

**它翻译的是 RPG Maker 的哪些字段**（这批字符串直接暴露了数据模型）：

```
command_name, currencyUnit, gameTitle, name, text, loadtext,
armorTypes, baseItems, equipTypes, elements, skillTypes, weaponTypes,
switches, variables, terms, plugins, json
```

**这对应 MV/MZ 的 `data/*.json`**：`Actors.json` / `Items.json` / `Skills.json` /
`System.json`（含 `terms` 术语表、`switches`、`variables`、`currencyUnit`）等。

**出现的游戏插件名**：`TorigoyaMZ_CommonMenu`、`YED_SkillShop` —— 说明它适配具体插件。

**实测验证（用用户的真实 MV/MZ 游戏 艾妮希雅）**：它翻译的字段与真实 `data/System.json`
**完全对得上**：

| RPGMakerUtils 的字段 | 真实 System.json 里的值 |
|---|---|
| `currencyUnit` | `"Ｇ"` |
| `gameTitle` | `"艾妮希雅与契约纹 v1.02"` |
| `terms` | 子键 `basic` / `commands` / `params` / `messages` |
| `armorTypes` / `skillTypes` / `weaponTypes` / `elements` / `equipTypes` | 全部存在 |
| `switches` / `variables` | 全部存在 |

**结论**：MV/MZ 的文本汉化**技术上完全可行**——文本就在 `data/*.json` 里，
结构确定、可读写。这比 MTool 的运行时注入温和得多：**改的是明文 JSON，不是进程内存**。


**注意**：它有 `TorigoyaMZ_CommonMenu` / `BB_CustomSaveWindow` / `DTextPicture` / `D_TEXT`
等插件名——说明**翻译要处理插件注入的文本**，不是只翻 `data/*.json`。

## 4. 关于「字体」：两家都做了，我们该重新评估 D35

**现状**：M3 的 D35 决定「`fontSub` 只做提示，不做自动修复」，理由：

> 实测 `fontSub` 是字体**替换映射**（`"Arial>Open Sans"`），不是目录加载器；
> 游戏自带 `Fonts/` 本就被 mkxp-z 自动加载。自动改会猜错反而添乱。

**但两家商业工具都把字体做成了独立功能**：

| 工具 | 做法 |
|---|---|
| MTool | 独立的 `fontSetting.exe`（**不是内嵌**，是单独程序） |
| RPGMakerUtils | 专门的 `editfontusercontrol` 界面 |

**它们处理的场景大概率是**：日文游戏在中文/英文系统上，缺日文字体 → **文字显示成方块**。
这跟 mkxp-z 的 `fontSub` 是**两个层面**：

| 层面 | 问题 | 解法 |
|---|---|---|
| mkxp-z | `fontSub` 是「替换映射」，不是「加载目录」 | 游戏自带 `Fonts/` 自动加载，一般够用 |
| **系统层** | macOS 缺日文字体（`MS Gothic` 等） | 需要**安装字体到系统**，或让引擎用替代字体 |
| MV/MZ | 游戏 CSS 里写死 `"MS Gothic"` 等 Windows 字体名 | 需要改 CSS 或注入字体 |

**修正判断**：

- D35 的原结论（`fontSub` 不是目录加载器）**仍然正确**
- 但**「字体问题」确实存在**，只是**解法不同**——不是改 `mkxp.json`，而是：
  1. **检测游戏要求的字体是否存在于系统**（读 `Fonts/` 文件名 + 常见 Windows 字体名黑名单）
  2. 缺失时提示「这个游戏需要 XX 字体，macOS 可能没有」
  3. 或者用 mkxp-z 的 `fontSub` 把缺失字体映射到系统已有的等价字体

**建议**：M3 的 D35 **不改**（不做自动修复），但可以在 M3 之后加**「字体缺失检测」**（等级 info，只提示）。

## 5. 最大的缺口：游戏内文本汉化

**两家都做了，我们没做，也没规划。**

### 5.1 两条技术路径（从样本推断）

| 路径 | MTool | RPGMakerUtils | 复杂度 | 风险 |
|---|---|---|---|---|
| **A. 静态表 + JS 插件注入**（MV/MZ） | — | ✅ `translations.json` + `JtJsonTranslationManager.js` → `js/plugins/` | 中 | **低**（改的是游戏目录里的插件文件，可逆） |
| **B. 运行时 DLL 注入**（通用） | ✅ `PIDDLLInject64.exe` | — | 高 | **高**（改游戏进程内存，可能被反作弊拦、可能崩） |

**对我们的意义**：

- **路径 A 与 M1 的 nwjs 模块高度契合**——那里已经有 `copyCheatFiles` / `modifyMVMainJs` 的注入逻辑
- **路径 B 不建议**——DLL 注入有法律与稳定性风险，且我们是「不改游戏」的定位

### 5.2 但有个**绕不开的前置问题**：翻译表从哪来？

静态汉化需要 `translations.json`，那是**人工翻译的产物**。三条路：

| 来源 | 可行性 | 问题 |
|---|---|---|
| 用户自己翻译 | ✅ 最安全 | 工作量大，大多数用户不会用 |
| 集成社区翻译（如 VNR / Translators++ 的库） | ⚠️ 需授权 | 社区翻译的授权状态不明；也可能是别人辛苦的成果 |
| **机器翻译 API** | ✅ 可做 | 要付费/限流；质量参差；且**整本游戏文本量大** |

**本鱼的判断**：这是**产品决策**，不是技术决策。技术上可行，但**先要做的是「格式与注入机制」**，
翻译来源可以后接（用户自填 / 导入外部 json / 未来接 API）。

### 5.3 最小可行版本（如果要做）

```
1. 识别 MV/MZ 游戏 → 读 data/*.json 的所有文本字段（terms/Actors/Items/…）
2. 生成一份「待翻译清单」JSON（原文 + 空占位）
3. 用户填完后，把 translations.json + 翻译插件放进 js/plugins/
4. 启动前确保插件被加载（改 package.json 或 plugins.js）
```

**但这一步要非常小心**：改 `js/plugins/` 等于改游戏文件。
建议**在游戏目录的副本上做**，或者**首次启用时明确告知用户「会修改游戏目录」并备份**。

## 7. 本文件没有做的事（诚实声明）

- **没有读第三方源码**：MTool 的核心加密，RPGMakerUtils 是编译后的 .NET
- **没有运行这两个工具**：本机是受限沙箱，无法执行 Windows GUI 程序
- **所有推断都标注了依据**：目录结构、配置内容、字符串、依赖库
