# module.js 还留着什么（M4.0 之后的残留盘点）

> **性质**：盘点。2026-04-07 用户点出：
> **「我们做 m4.0 本来就是为了摆脱 xenolauncher 的依赖……既然搞了这么一出，
> 就别给我小偷小摸偷偷藏着还有本来我们决定不要了的东西」**
>
> 本文件不含代码改动，只把「还留着什么、每样能不能删」列清。

---

## 1. 现在的真实依赖图

```
resources/core/module.js   1911 行（73 KB）
        ↓  18 个 API 被调用
src/main/core-host.ts / ipc.ts
```

**M4.0 砍掉的**：`launcher.js`（启动逻辑）→ 已自实现
**M4.0 没砍的**：`module.js`（1911 行）→ **仍在用，18 个 API**

---

## 2. 18 个 API 按用途分类

### A 类：**引擎识别**（4 个）—— 自己实现很容易

| API | 做什么 | 自己实现的难度 |
|---|---|---|
| `readLocalManifests` | 读 `<modules>/<引擎>/manifest.json` | 🟢 就是 `fs.readdir` + `JSON.parse` |
| `detectEngineForPath` | 按 autodetect 规则判断某个路径是哪个引擎 | 🟢 比对文件/扩展名，约 30 行 |
| `detectEngineFromAutodetectMap` | 同上，用远程规则的版本 | 🟢 同上 |
| `fetchModulesForAutodetect` | 拉远程规则 | ❌ **M4.1 已决定删掉**（清单自己维护） |

**结论：A 类可以全部自实现，且 M4.1 本来就要动这块。**

### B 类：**模块安装/更新**（6 个）—— 中等复杂

| API | 做什么 | 难度 |
|---|---|---|
| `installModuleWithProgress` | 下载 manifest + 生成目录 + 装依赖 | 🟡 manifest 变成自己生成后，只剩「生成目录 + 装依赖」 |
| `uninstallModule` | 删模块目录 | 🟢 `fs.rm` |
| `updateModulePreservingMultiversionsWithProgress` | 更新但保留多版本 deps | 🟡 **有真实复杂度**（multi-version 目录不能覆盖） |
| `updateDependenciesTaskWithProgress` | 更新已装依赖 | 🔴 **已知坏**（D38：只更新已装的，从没装过的它一个字节都不下） |
| `checkDependencyUpdatesForFolders` | 检查依赖有无更新 | 🟡 要拿远端版本对比 |
| `invalidateDepUpdatesCache` | 清依赖检查缓存 | 🟢 一个 `Map.clear()` |

**注意 `updateDependenciesTaskWithProgress`**：我们**已经在 `ipc.ts` 里自己实现过** `installDependencies(folder, wanted, signal)`（M3 时写的，因为上游那个是坏的）。

### C 类：**依赖下载/解压**（在 module.js 内部，通过 B 类间接使用）

这部分是 `module.js` 里最实在的：下载、解压、事务回滚、进度上报。
**但它有个前提**——吃的是「manifest 里的 dependencies 定义」。M4.1 之后那个 manifest 是我们自己生成的，所以它只是「执行器」，不含任何上游数据。

### D 类：**杂项**（4 个）—— 都简单

| API | 做什么 | 难度 |
|---|---|---|
| `getInstalledModuleFolders` | 列已装引擎 | 🟢 `fs.readdir` |
| `getModulesDir` | 返回 `<dataDir>/modules` | 🟢 一个 `path.join` |
| `hasUpdate` | 版本号比较 | 🟢 约 20 行（也能用现成实现） |
| `reconcileAndPersistGameArgs` | 按 manifest 的 gameArgs schema 补缺省值并落盘 | 🟢 有 registry 之后更简单 |
| `deleteWithEngine` | 删游戏时清理引擎相关 | 🟢 看实现 |

### E 类：**还在从上游拉**（1 个）

| API | 做什么 |
|---|---|
| `fetchRemoteManifestsList` | **M4.1 明确要删掉的** |

## 3. 所以"彻底摆脱"有两条路

### 路 A：M4.1 只删 manifest 拉取，保留 module.js

| 砍掉 | 保留 |
|---|---|
| `fetchRemoteManifestsList` | 其余 17 个 API + 1911 行 module.js |

**收益**：那三个引擎在代码里不存在了（D60）
**代价**：`resources/core/module.js` 还在，仍是上游代码（GPL fork）

### 路 B：连 module.js 一起删（自己实现全部 17 个 API）

| 砍掉 | 工作量 |
|---|---|
| `resources/core/module.js`（1911 行） | **全部 17 个 API 自实现** |

**收益**：**真正的零上游**——`resources/core/` 整个目录可以删
**代价**：工作量最大的是 B 类里那 2 个（`updateModulePreservingMultiversionsWithProgress` 的多版本保留、`checkDependencyUpdatesForFolders`）。

**有利条件**：
- D38 里我们**已经自己实现了** `installDependencies`（因为上游那个是坏的）
- M3 里已经自己实现了 `extractArchive` 的调用与事务回滚
- 引擎只有 4 个，不是 7 个

---

## 4. 本鱼的判断

**路 B 可行，且工作量比看起来小**。理由：

| 部分 | 状态 |
|---|---|
| 依赖下载 + 解压 + 进度 | ✅ **M3 已自实现**（`installDependencies`） |
| 引擎识别 | 🟢 简单，M4.1 本来就要写 |
| 模块目录管理 | 🟢 `fs` 操作 |
| 版本号比较 | 🟢 约 20 行 |
| manifest 生成 | ✅ M4.1 D62 已决定自己生成 |
| **多版本保留更新** | 🟡 **唯一有真实复杂度的一块**（nwjs 的 `deps/version/v0.106.1` 不能被覆盖） |
| 依赖更新检查 | 🟡 需要拿到「远端版本」——**但我们不再有远端清单了**，所以这个功能其实可以**删掉** |

**关键洞察**：既然不再从上游拉清单，**「检查依赖更新」这个功能就没有意义了**（没有远端可比）。所以 B 类里最麻烦的两个，一个是自己写多版本保存、一个直接删。

→ **路 B 的实际工作量 ≈ M4.1 的 1.5 倍，不是 5 倍。**

## 5. 建议：把 M4.1 扩成「彻底摆脱上游」

| 子项 | 内容 |
|---|---|
| **M4.1a** | 4 个引擎自己维护（原计划） |
| **M4.1b** | 17 个 core API 自实现（`src/main/engines/`） |
| **M4.1c** | **删 `resources/core/`** 整个目录 + `FORK-NOTES.md` |
| **M4.1d** | 删「检查依赖更新」功能（没有远端可比了） |

**完成后**：项目里**没有任何一行上游代码**。

**代价（必须说清）**：
- 引擎版本要自己维护（已接受，D60）
- 「检查引擎更新」功能消失（改成「本地版本 vs registry 硬编码版本」的简单对比）
- **D2（接受 GPL-3.0 复用上游）这条决策作废** —— 项目变回自己写，GPL 约束也消失（但仍需保留 LICENSE 里对历史来源的说明）
